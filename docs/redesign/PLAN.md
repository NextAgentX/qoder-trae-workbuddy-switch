## 0. 结论先行

三句话：

1. **把「产品 × 区域」压成一个概念——作用域（Scope），搬到顶部应用栏。** 侧栏只留 5 个固定目的地，不再随产品换血。
2. **把两套逐字复制的页面合并成「能力驱动的工作台」。** 页面组件只写一份，平台差异由注册表里的能力开关表达，而不是靠 `if (isTrae)` 或复制文件。
3. **新增一个平台 = 加一条注册数据 + 后端补一个模块目录，页面组件零改动。**（v2.1 修正：这句话只覆盖**页面**；`api.ts` / 词条 / 演示数据 / 网关组件 / 缓存键 / 后端存量注册点仍要改，实测清单见 §4。）
4. **新增一个功能 = 加数据、不改逻辑。**（v2.1 新增：目的地 / 能力开关 / 视图参数 / 图表四条扩展路径见 §4.2。）

一句话原则：**一个维度，只在一个层级，以一种形态，出现一次。**

### 三个可度量的收益

| 指标 | 现状 | 目标 |
|:---|:---|:---|
| 跨数据域任务（WorkBuddy 国内版·账号 → Trae 国际版·用量） | 4 次点击，**顺序不可交换** | 3 次点击，顺序自由 |
| 作用域状态容器 | 3 套互不通信（组件 state / 各页 localStorage / URL 查询参数） | 1 套（URL 为唯一真值） |
| 页面组件份数（10 个路由） | 10 个文件、两套 5:5 复制 | **5 个工作台，两个平台共用** |
| 新增平台的前端改动点 | ~10+ 文件 | **≥ 5 处**（v2.1 修正，初稿写「2 处」；实测清单见 §4.1） |
| 新增平台的**新增命令**注册点 | 6 处注册表逐个登记 | **2 处**（1 张 ProductSpec 表 + 1 个模块目录） |
| 新增平台的**存量**注册点 | — | **不减**（别名转发保留旧条目；后端另有 ≥10 处必改点，见 §4.1） |
| 新增一个**功能**的改动点 | 无统一路径 | **≤ 6 处，且全是加行、无改逻辑**（§4.2） |
| 侧栏产品名截断 | 存在（源码注释实测 195px 放不下 `WorkBuddy`） | 消除 |

**诚实说明边界**：这不是「数量级」的步数优化（4→3）。主要收益在**一致性、状态正确性、认知负担与扩展成本**。跨数据域是低频动作，但「切了区域却在另一个页面看不到」是一类**静默错误**——它不报错，只会让用户做出错误判断。

> ⚠️ **v2.1 再诚实一次**：「注册表从 6 处收敛到 2 处」这句话**只对新增命令成立**。
> 存量注册点一个都减不掉（旧命令名保留为别名），且**前端还有 ≥5 处、后端还有 ≥10 处**是初稿完全没数的。
> 参数化的真实收益是「新增命令不再逐个登记」，不是「新增平台只需改 4 个文件」。详见 §4。

### 1.1 三个轴，散在三个层级、三种状态容器

| 维度 | 取值 | 当前载体 | 状态归属 |
|:---|:---|:---|:---|

### 1.2 八个具体问题（每条带源码证据）

1. **两级切换 + 顺序锁定。** 换数据域要「选产品 → 选区域」两次定位；Trae 侧还多一层——程序位按钮**只按当前区域渲染**（`TraeAccountsPage.tsx:663-686`），所以「把 TraeCode 国际版切到账号 X」必须**先切区域**才能看见按钮，**3 步且顺序不可交换**。

2. **同一维度三种形态、两种语义。** 账号页是「两行大 Tab + 状态圆点」，统计页是「单行 `RegionBar`」，Trae 是 `TraeVariantBar`，切换弹窗里还内嵌一份 Tabs（`switch-account-dialog.tsx:411-424`）。而且账号页只有 `cn/global`，统计页多出 `all`——**同一概念两种语义**。

3. **状态不共享（最严重）。** 用户在账号页切到国际版，进 Token 统计页看到的仍是国内版。这类错位**不报错、不提示**。

4. **`variant` 一词双义。** `TraeVariantId` 是「区域 ∪ 程序位 ∪ 历史产品线名」的并集（`trae-types.ts:60-76`，作者自陈「区域与程序位共用一个字段」）。同一字段在不同接口含义不同：`TraeVariantStatus.variant` 是区域，`TraeProgramStatus.variant` 是程序位。`traeVariantLabel("cn")` 返回「国内版」，`traeVariantLabel("trae_cn")` 返回「TraeCode」。

5. **两套页面逐字复制。** 侧栏 5:5（`App.tsx:113-128`）、路由 5:5（`App.tsx:524-536`）、Trae 卡与 WB 卡同构（作者自陈 `TraeAccountsPage.tsx:125-149`）。**任何功能都要做两遍**，且已经漂移：Trae 有分组筛选、签到进度就地展开卡、旧库合并迁移；WB 有自动旅行、按版本双条目、accountStrategy。同一件事在两个产品上出现在不同位置。

6. **API 服务页 = 6 张卡纵向堆叠**（`ApiServicePage.tsx:186-307`），无 Tab、无子导航、无锚点。

7. **账号卡片可点区 ≥ 10 个**（`account-card.tsx`）：更多菜单、5 类状态 chip、备注按钮、查看全部资源包、3 枚程序位按钮（紧凑模式还有 3 枚图标按钮）、当前账号徽章 header/footer **各一份**。而且 **WB 侧无搜索、无排序、无分组、无批量操作**（排序是写死的「自动积分优先级」`AccountsPage.tsx:745-784`）。

8. **状态语言不统一。** 加载态 5 种写法（Loader2+文案 / 骨架屏 / 纯文本 / 底部 Loader2）；「保存失败」在设置页是 toast、签到卡是行内 Alert、账号页是页面级 Alert；空态只有账号页有结构化卡片，其余是单行虚线框。

### 1.3 扩展性诊断：区域维度已做对，产品维度没抽象

**已经做对、必须保留：**

- `RegionSpec` / `VariantSpec` / `ProgramSpec` 三张表（`core/modules/region.rs:142`、`trae/variant.rs:398`、`trae/region.rs:178`）——加区域是**改数据不是改逻辑**，0 个新文件。
- `region_scoped_file_name()` 后缀规则（`crates/buddy-switch-core/src/modules/trae/paths.rs:100`）——新区域自动获得文件命名。
- `region()` / `variant_for_program()` 显式映射 + 单测钉死。
- core / gateway / server / tauri 四层分离，核心逻辑三宿主复用。

**明显的单产品硬编码：**

- **`BackgroundTask` 是扁平枚举**（`src-tauri/lib.rs:40`、`server/main.rs:42`，两份逐字重复），出现 `TraeCreditsRefresh` 这种「产品名进枚举名」的条目。
- **命令面成对复制**：117 条 Tauri 命令中 48 条 Trae 前缀；**99 条 server 路由中 45 条 `/api/trae/*`（36 条业务 + 9 条网关）**。
  但 `get_accounts` ↔ `get_trae_accounts` **不是全部一一对应**——48 条 Trae 命令中约 18 条（保守）概念上 Trae 独有
  （`trae_merge_legacy_regions` / `trae_group_op` / `trae_refresh_jwt` / `trae_clear_cooldown` / `trae_reset_device` /
  `trae_backup|restore|delete_profile` / `get_trae_variants|capabilities|env|client_models` / `trae_save_login` /
  `trae_oauth_cancel` …），WB 侧无同名概念，**无法并入 `cmd(scope)`**。详见 §2.4。
- **网关宿主是「平行且有意不复用」，不是「逐字复制」**：`gateway_host.rs` 与 `trae_gateway_host.rs` 各 91 行，
  但 `trae_gateway_host.rs:3` 自述二者平行、**互不复用**——理由是 axum 同路径 `merge` 会 panic（两个 router 若
  都声明同一路径，合并即失败）。**且共有两对，不止一对**：crates 侧一对，`src-tauri/gateway.rs`(84 行) +
  `trae_gateway.rs`(88 行) 是第二对。方案 P5 若只处理 crates 侧会漏掉一半。
- **WB 侧的程序位是硬编码模块**：`codebuddy_cli.rs`(1263 行) / `codebuddy_cn_ide.rs`(1303 行) / `vscode_cn_inject.rs`——复用 WB 账号库但**没有表驱动**，第三个程序位无处安放。
- **`TraeVariant` 单轴与 `TraeRegion`×`TraeProgram` 双轴并存**（`trae/variant.rs:611` 自述「过渡态」），新旧两套遍历入口易误用。

**结论**：加**区域**在 Rust 侧近零成本（数据表 + 后缀命名），但**端到端不为零**——前端还需改
`src/lib/region.ts` 的 `REGION_DESCRIPTORS`、i18n 词条（`shared.region.*`），Trae 侧还需动 `region.rs` 的 region 轴。
加**平台**则要走「复制 trae 模块（28,029 行）+ 改**至少 10 处**注册点」的路（实测清单见 §4）。这是当前架构最大的扩展瓶颈。

## 2. 目标架构

### 2.1 四层模型

| 层 | 名称 | 内容 | 载体 | 是否全局 |
|:---|:---|:---|:---|:---|
| **L0** | 应用 | 语言 / 外观 / 开机自启 / 自动更新 / **更新代理 / 最小化到托盘 / 关于 / 捐赠**（v2.1 补，初稿漏了这四项） | 顶栏溢出菜单 | 是 |
| **L1** | **作用域 Scope** | `平台 × 区域`，如 `wb-global` / `trae-cn` | **顶部应用栏** | 是，全应用唯一 |
| **L2** | 目的地 Destination | 概览 / 账号 / 用量 / 网关 / 设置 | 侧栏（固定 5 项） | 是 |
| **L3** | 视图参数 View param | 时间范围 / 数据来源 / 分布维度 / 合并开关 / 程序位 | 页面内参数条、卡片内按钮 | 否，页面私有 |

**为什么是「作用域」而不是「产品 + 区域」**：每个组合拥有**独立的账号库、认证文件、配置**，彼此互斥。用户心智是「我现在管的是哪一套账号」，不是「我选了哪个产品、再选了哪个版本」。压成单层枚举既符合 Hick 定律，也让「状态只有一个真值」成为可能。

**为什么程序位不进 L1**：区域决定「账号属于哪套体系」，程序位只决定「落到哪个客户端」。它是**操作参数**，留在操作处是对的。但 v2 修一处 v1 没提的问题：**程序位不该被区域隐藏**——见 §3.3。

### 2.4.1 「注册表从 6 处收敛到 2 处」的**真实口径**

v2 初稿这句话**只对「新增命令」成立，对存量一个都不减**。实测后的准确说法是：

| 口径 | 真实情况 |
|:---|:---|
| 新增平台的**新增命令**注册点 | 参数化后确实只需 1 张 `ProductSpec` 表 + 1 个模块目录 ✅ |
| **存量**注册点 | **一个都减不掉**——别名转发意味着旧 `generate_handler!` 条目、旧 `.route` 条目、旧 ROUTES 条目全部保留 |
| 前端注册点 | 不是 2 处，见 §4 实测清单（**≥5 处**） |
| 后端注册点 | 不是 2 处，见 §4 实测清单（**≥10 处**） |

所以 §0 表格里「新增平台的后端注册点 6 → 2」应改读为：
**「新增平台**新增能力**的注册点 6 → 2；**存量**注册点不变；**前端**注册点另有 ≥5 处（v2 初稿漏计）」**。

### 2.5 安全边界（v2.1 新增，P5 前置条件）

把「作用域」从前端参数升格为**唯一数据域选择器**，会让一个拼写错误直接变成「静默操作错误的数据域」。
所以下面四条是 P5 的**硬前置**，不是可选优化：

**(1) scope 解析必须 fail-closed。**
现状三处解析**全部 fail-open**（未知 / 空 / 缺 → 回落 `Cn` / `TraeWork`）：
`src-tauri/src/commands.rs:22-40`、`core/modules/region.rs:129-131`、`server/src/api.rs:265-286`。
参数化后，`accounts_list("trae-glboal")` 会**静默读写 `trae-cn` 的库**——用户会看到「账号凭空消失」。
⇒ `Scope::parse` 一律返回 `Result`，未知 / 空 / 缺 **Err 拒绝**，**绝不 default**。
这与既有先例一致：`BUDDY_SWITCH_HOME` 非法时独立服务**拒绝启动**（exit 2），而不是静默回落。

**(2) capability 必须在命令分发层校验，不能只靠 UI 隐藏。**
后端现有 `platform.rs:1326` 的 `capabilities()` 只是**诊断用的 unsupported 列表**，不是执行门控；
Tauri 自定义命令对 webview **全可达**。⇒ 新平台漏配 `accountDelete` 时，UI 不显示按钮，
但命令**仍可被调用**——能力被静默开启。
⇒ `ProductSpec.capabilities` 必须在**命令分发入口**校验：缺能力 → `Err`（**默认拒绝**）。

**(3) 破坏性操作要有后端支撑，不能只有 UI 承诺。**
`core/.../account.rs:40-48` 的 `delete_account_from_path` 是硬 `retain` + 原子覆写，**无回收站 / 软删除**，
现有文案明写「此操作不可撤销」。而 §3.5 承诺「成功后 toast 可撤销」——**后端没有任何支撑**。
⇒ 二选一：实现软删除（移入 `accounts.trash.<region>.json`），或删除前自动快照；
批量删除 > N 条需二次确认；每次破坏性操作记录 `scope + 数量` 审计日志。
⇒ 另注：删除只匹配 `id`，而查找 / 备注匹配 `id` **或** `uid`——按 `uid` 选批删会**静默空转**，需统一。

**(4) 跨作用域选择集必须按 `(scope, id)` 键控。**
§3.4 批量条与 §3.7 命令面板都支持跨作用域。若选中态只存 `id`，切到另一个作用域后点「批量删除」
会用 A 的 id 打 B 的库（或静默空转）。⇒ 选中集合键 = `(scope, id)`，**切换 scope 即失效清空**。

> ✅ **已做对、P5 必须守住的隔离根基**：所有路径都由**类型化枚举**派生，raw scope 字符串**从不进路径**
> （`core/modules/region.rs:242`、`core/modules/trae/paths.rs:71-113`）；账号 / 凭据 / 快照 / 缓存均按 region 分家；
> server 仅绑 `127.0.0.1`；`safe_slot_name` 拦路径穿越。P5 改造时**唯一不能破的规则**是：
> **「字符串 → 解析成枚举 → 查表派生路径」，中间任何一步都不许用原始字符串**。

### 2.6 全局备份的数据契约（v2.2 新增）

**为什么不能直接打包 `store` 目录的原始文件**：

1. 原始文件含凭据与缓存，**无法提供「不含凭据」的开关**（那是本需求的硬要求）；
2. 原始文件格式随版本自由演化，**没有稳定契约**，跨版本导入必碎；
3. 无法做**选择性导出**（只导某几个作用域、或只导账号不导配置）。

⇒ 采用**结构化 JSON envelope**，内部复用现有 `merge_import_record` 的合并语义（缺键即保留本地值）。

**文件形态**：

```jsonc
{
  "kind": "buddy-switch-backup",       // 文件类型标识，导入前先校验，避免误导入任意 JSON
  "formatVersion": 1,                  // 契约版本，单调递增
  "appVersion": "2026.10.1",           // 产出该文件的应用版本（仅用于提示，不参与判断）
  "exportedAt": "2026-10-01T14:00:00Z",
  "includesCredentials": false,        // 是否含 token；导入时据此决定是否提示「需重新登录」
  "scopes": {
    "wb-cn": {
      "accounts": [ /* 账号记录，字段与现有 export_accounts 同源 */ ],
      "config": {
        "checkin":    { /* checkin_config_file      */ },
        "travel":     { /* travel_config_file       */ },
        "autoRotate": { /* auto_rotate_config_file  */ },
        "switch":     { /* switch_config_file       */ }
      },
      "gateway": { "keys": [], "models": [], "pool": [] }
    },
    "wb-global": { /* … */ }, "trae-cn": { /* … */ }, "trae-global": { /* … */ }
  },
  "appSettings": { /* 语言 / 外观 / 开机自启 / 自动更新 / 托盘 / 代理 */ }
}
```

**四条契约规则**：

1. **按 scope 分组，而不是按平台。** 与 §2.1 的作用域模型同构；导出时**遍历注册表**（`SCOPES`）——
   因此**新增平台或区域时备份自动覆盖它，备份代码零改动**。这正是「方便拓展」在备份这一层的落点。
2. **`formatVersion` 是唯一兼容依据**（fail-closed，与 §2.5 同源）：
   - `formatVersion > 支持上限` ⇒ **拒绝并提示升级应用**，不做「尽力解析」；
   - `< 当前` ⇒ 走迁移函数逐版升级；
   - 缺 `kind` 或 `kind` 不匹配 ⇒ **拒绝**（防误导入任意 JSON）。
3. **凭据是「可选字段」而不是「可选结构」。** `includesCredentials=false` 时，账号记录里
   **完全不出现** `accessToken` / `refreshToken` / 信封字段的键（不是写成 `null`）——
   这样「文件里搜不到该键」才能作为一条**可证伪的验收断言**（见 §6）。
4. **导入按 `uid` 去重**（账号的稳定身份），冲突四选一：新增 / 覆盖 / 跳过 / 保留两者。
   ⚠️ 现有实现存在不一致：**删除只匹配 `id`，而查找 / 备注匹配 `id` 或 `uid`** ——
   全局导入必须统一到 `uid`，否则会出现「导入进来了但删不掉」。

**为什么不额外提供「打包整个 store 目录」的第二种格式**：一份契约、一个入口。
多格式会让「拿到文件不知道该用哪个」变成新的支持成本。

### 2.7 两个开关别混：平台能力 ≠ 用户偏好（v2.3 新增）

v2 初稿把两件事都叫「能力开关」，这是个**会写错代码**的混淆。它们是**两个正交的维度**：

| | 平台能力 `capabilities` | 用户偏好 `preferences` |
|:---|:---|:---|
| 谁决定 | **平台固有**——Trae 有签到、WorkBuddy 有自动旅行，这是事实 | **用户自己选**——我用不用 CodeBuddy CLI |
| 存放 | `PlatformDescriptor`（**代码里的注册表**） | **本地偏好**（localStorage），不进注册表 |
| 改错了会怎样 | 是**代码错**：不该有的功能出现了 | 只是显示变化，**数据与账号库不受影响** |
| 默认值 | 由平台决定，**用户不可改** | 有默认值，**用户可改** |
| 校验位置 | **后端命令分发层**（§2.5 第 2 条：缺能力 ⇒ `Err`） | 纯前端；后端**不该**因为用户关了入口就拒绝命令 |

**为什么这个区分是硬的**：用户关掉「CodeBuddy CLI」入口，只是不想在界面上看到它；
他**并没有**放弃这个能力——若他直接调命令或走 URL，功能应当照常工作。
反过来，一个平台**没有**会话复制能力，那不管用户在设置里怎么点，都不该冒出会话复制。

**落地形态**：

```ts
// 平台能力（注册表，代码里声明，用户改不了）
platform.capabilities.includes("sessionCopy")

// 用户偏好（本地，可改，有默认值，不影响数据）
preferences.tools["codebuddy-cli"]  // 默认 false（灰度）
preferences.nav["sessions"]       // 默认 true
preferences.accountDisplayField   // "note" | "phone" | "nickname"
```

**两类偏好的统一语义**（照抄现有实现里那条已经正确的规则）：

> 关闭某个入口 = **该入口不渲染、相关状态轮询跳过**；
> **页面仍可经 URL 直达，数据与账号库都不受影响，重新打开即恢复。**

**必须避免的三个错误**：

1. ❌ 把用户偏好塞进 `capabilities` —— 会让「关掉入口」变成「功能消失」；
2. ❌ 把平台能力做成用户开关 —— 会让用户打开一个**根本不存在的功能**；
3. ❌ 关闭入口时顺手停掉后台任务 —— 轮询可以跳，**保活 / 签到这类写状态的任务不能停**。

```
○ [◆] WorkBuddy 国际版      未登录 · 2 个账号

○ [▲] TraeWork 国际版       未检测到 · 0 个账号
```

- 固定在顶栏左一（Fitts 定律：位置稳定）。
- 关闭态显示：产品图标 + 作用域名 + 运行状态点。
- 快捷键 `Ctrl/Cmd + 1..4` 直切；**不替代**侧栏（可发现性要求主导航常驻可见）。

#### ★ 平台窗口约束：作用域按钮**不能贴左缘**（v2.1 修正）

原方案说「顶栏左一」，但**与 macOS 系统红绿灯物理冲突**：

- `src-tauri/tauri.conf.json:21-27` 配置了 `"titleBarStyle": "Overlay"` +
  `"trafficLightPosition": { "x": 16, "y": 30 }` ⇒ 红绿灯落在窗口左上角约 **x∈[16,76]、y∈[16,44]** 的区域。
- 顶栏高 56px，作用域按钮若从 x=0 起排，**正好被红绿灯压住**（不可点、不可读）。
- 现状实现是靠侧栏 `pt-20` 避让（`src/App.tsx:437-448`），顶栏本身没有避让逻辑。

**规则**：

| 平台 | 顶栏左内边距 | 说明 |
|:---|:---|:---|
| macOS | **≥ 76px** | 让开红绿灯；若 `trafficLightPosition` 调整，此值同步 |
| Windows / Linux | 8–12px | 无红绿灯，正常留白 |

实现方式：读 `platform` 决定 padding（Tauri `@tauri-apps/plugin-os` 或已有的平台判断），
**不要写死常量**。原型 `demo-app.js` 演示的是浏览器环境，无红绿灯，故看不出这个问题——
**这是「jsdom 不做布局」抓不到、必须靠真机截图确认的一类问题**（见 §8）。

#### 快捷键的可扩展性（v2.1 修正）

`Ctrl/Cmd + 1..4` **硬绑 4 个作用域**，而 §4 的 Playbook 恰恰要求「加平台」——
加到第 5 个作用域时快捷键方案立刻失效。改为：

- 按**作用域在注册表中的序号动态生成** `Ctrl/Cmd + 1..N`（N = 当前作用域总数）。
- 作用域 > 5 个时，**降级为不绑定**（只在选择器菜单里显示序号提示），避免与浏览器/系统快捷键冲突。
- 提供设置项可关闭（用户可能用 `Ctrl+1..4` 切浏览器标签页的习惯）。
- Tauri webview 内需实测与系统快捷键的冲突面（尤其 Windows 的 `Ctrl+1..9` 与 macOS 的 `Cmd+数字`）。


### 3.2 侧栏：**可配置**的目的地集合 + 状态徽章

**默认 6 项**：概览 / 账号 / 用量 / **会话** / 网关 / 设置。

> **v2.3 修正**：v2 初稿写「固定 5 项」。但产品里还有一整个**会话管理**功能族
> （跨账号会话复制 / 关联 / 增量同步 / 分歧处理），它既不属于「账号」也不属于「用量」——
> 硬塞进任何一项，都会让那一项变成「什么都装」的杂货铺。
> ⇒ 侧栏从「固定 5 项」改为 **「一组可配置的目的地，默认 6 项」**。

**为什么是「可配置」而不是「固定」**：

- 不同用户实际启用的客户端数量不同：只用 WorkBuddy 的人不需要会话页；装了 5 个客户端的人需要。
- 现有实现里已经有同款语义的偏好：**关掉某个导航入口后该入口不渲染，
  但页面仍可经 URL 直达，数据与账号库都不受影响，重新打开即恢复。**
  这个语义是对的，应当**上提为通用能力**，而不是只给某一项开小灶。

**四条规则**：

1. 目的地集合 = `PlatformDescriptor.destinations`（平台声明有哪些）× **用户可见性偏好**（本地持久化）。
2. 关闭某项 = **不渲染入口**；**URL 直达仍然可用**（避免「关了就没法访问」的死胡同）。
3. 徽章承载「有事情要处理」：账号数、过期数、**会话待同步数**、Key 数。
4. **至少保留 1 项**：不允许把侧栏关空（否则用户回不来）。关到最后一项时该开关禁用并说明原因。

底部保留：版本号 + 状态点 + 应用设置入口（**留在侧栏底部还是迁顶栏，见 §7 决策 3**）。

#### ★ 客户端（程序位）清单：**现状 5 个 + 待新增 2 个**（v2.6 两度修正后的最终口径）

> ⚠️ **本节经过两次修正，最终口径如下（2026-10-03）**：
>
> 1. v2.3 初稿写「程序位不是 3 个，是 5 个」—— 错在**措辞把「目标」写成了「现状」**；
> 2. v2.6 我一度把它当成事实错误**整节删掉**，**也是错的** —— 用户澄清：
>    **那正是「参考同源实现、把 VS Code 支持加进来」的目标**。
>
> ⇒ 正确写法是**分列「现状」与「待新增」**，并写清新增的**技术前提**。
>
> **两条教训**（方向相反，都值得记）：
> - 把**目标**写成现状 ⇒ 实施者以为"已经有了、只是没做页面"（§3.15 的会话能力就栽过这个）；
> - 把**目标**当成错误删掉 ⇒ 丢掉需求（本轮栽的就是这个）。

**A. 现状（本仓已有，逐文件核实）**：

**新增的 VS Code 插件若要支持会话复制，前提同样是"有等价的数据三件套 + 云端归属"**（§3.15 能力边界）——
**不要因为"客户端能切换了"就默认它能复制会话。**

**由此得出三条设计规则**：

1. **客户端清单必须从注册表读，不许在页面里硬编码**（§2.3）。
   写死清单 ⇒ 下次新增客户端必然漏改——本节这个错误本身就是证据。
2. **「需要重启客户端」是一个维度，不是所有客户端都适用**：CLI **不重开**且会中断会话，
   文案必须如实说明（**不能沿用「自动重开」的措辞**）⇒ 统一的重启确认流程见 §3.15.3。
3. **客户端可被用户关闭**（§2.7 的**用户偏好**）—— 与「平台是否具备该能力」（**平台固有**）是两个维度，
   别混。

#### ★ 账号显示字段与邮箱脱敏（v2.3 新增）

**显示哪个字段应当是用户可配的**（备注 / 手机号 / 账号名），
回退链固定为 **选定字段 → 账号名 → uid → id**，
且**所有展示账号名的位置共用同一个函数**（卡片、切换弹窗、选择列表、批量条）——
否则「卡片上叫 A、切换弹窗里叫 B」是一类新的静默错误。

**邮箱默认脱敏**：本地段只留首字符（`j******@example.com`）。这是**展示层的隐私默认**，
不是安全边界（真实值仍在本地库），但能避免**截图 / 投屏 / 求助时泄露完整邮箱**——
这类泄露在本项目里是真实高频场景（用户经常贴截图报障）。

### 3.4 账号列表工具栏（新增能力）

搜索（自动聚焦，`/` 唤起）· 排序（积分优先级 / 名称 / 到期时间 / 最近使用）· 分组（无 / 按程序位 / 按状态 / 自定义组）· 视图切换（卡片 / 表格）· 批量操作条（勾选后浮现：批量刷新 / 批量签到 / 批量导出 / 删除）。

**排序与分组是纯客户端视图能力**，不改后端契约。当前写死的「自动积分优先级」成为排序的**默认选项**，而不是唯一选项。

#### ★ 四条列表通用规则（v2.3 新增，账号 / 会话 / 日志三处共用）

这四条来自实际实现里已经验证过的做法，**三个列表都要遵守**，不要各写一套：

1. **筛选选项按需出现**：某个筛选值在当前数据里**一个都没有**时，**不渲染该选项**。
   「点了永远是空」的假选项是噪声，还会让人以为功能坏了。
2. **分页阈值隐藏**：少于阈值（约 8 条）**不分页**，也不显示「显示 1–N，共 M」。
3. **空态分两种文案**（这条最容易写错）：
   - **真的没有数据** → 「还没有 X」+ **如何产生第一条**的引导（带按钮）；
   - **有数据但被筛没了** → 「没有符合条件的 X」+ 「清除筛选」。
   两者混用会让用户以为**数据丢了**——这是 §3.6「静默错误」在列表层的版本。
4. **骨架屏的形状要接近真实内容**（卡片网格给卡片骨架、表格给行骨架），
   否则会出现「加载完跳一下」的布局位移。禁止用居中 spinner 占位。

|:---|:---|:---|
| 账号详情 / 资源包 / 签到历史 | 卡片内联 + 多个 Dialog | 右侧抽屉（列表上下文保留） |
| 切换账号 | 模态 Dialog，单页多区块（来源版本 / 复制会话 / 记忆 / 连接器 / 三层会话树） | 抽屉内**三步向导**：目标 → 迁移内容 → 确认 |

### 3.6 统一状态语言（消除 5 种加载态）

基础四态：

| 状态 | 唯一形态 |
|:---|:---|
| 加载 | `<Skeleton>`（列表用骨架卡，表格用骨架行，禁止纯文本「加载中」） |
| 空 | `<EmptyState icon title description action>`（全应用一个组件） |
| 错误 | 需要用户决策 → 行内 `<Alert>`；瞬时失败 → `toast.error`（带重试 action） |
| 成功/瞬时 | `toast.success`；**可逆**的破坏性操作 → `toast` 带**撤销** action |

#### ★ 补齐五种「难状态」（v2.1 新增）

v2 初稿只定义了四态，但原型里**已经实现了**其中几种（§8 的「部分失败」「权限错误升级引导」），
规范没沉淀 = 下一轮接手会丢。补齐如下：

| 状态 | 唯一形态 | 关键约束 |
|:---|:---|:---|
| **权限态** | 行内 `<Alert variant="warning">` + 「去授权 / 提权」CTA | 若需等待用户操作后自检，给**轮询指示**（每 2s 自检），不要只给一个死按钮 |
| **部分失败态** | 汇总条 `N 成功 / M 失败` + 「重试失败项」+ 可展开失败明细 | 批量操作的**默认反馈形态**；不许只 toast 一句「部分失败」 |
| **冲突态** | 行内 `<Alert>`「已被其他操作修改，请刷新」+ 刷新按钮 | 乐观更新失败时的统一出口 |
| **过期态** | 卡片/行内 `<Badge variant="danger">已过期</Badge>` + 「重新登录」CTA | **已过期账号不得再给「手动签到」**（与批量签到口径矛盾，原型里抓到过） |
| **超时态** | `toast.error` + 重试 action；连续超时 → 升级为行内 `<Alert>` + 诊断入口 | 与「瞬时失败」的区别是**重试仍失败** |

#### ⚠️ 两条适用面（2026-10-03 实测后补）

**① `EmptyState` 只用于「区块级空态」**，不是"所有没有数据的地方"：

| 场景 | 该用什么 |
|:---|:---|
| 列表 / 表格 / 卡片区没有数据 | ✅ `EmptyState`（图标 + 标题 + 说明 + 出口） |
| **卡片内的一行小字**（如「无资源包」） | ❌ 不用 —— 空间小，图标会挤 |
| **行内 span**（如排期某小时无内容） | ❌ 不用 —— 不是区块级 |
| **已有更丰富形态的**（如「标题 + 可能原因列表 + 出口」） | ❌ **不要降级替换** —— 它比 `EmptyState` 更强 |

**② 「加载态」与「按钮操作中」是两类，别混**（本仓实测：65 处 `<Loader2>` 多在按钮内）：

| 状态 | 唯一形态 | 判据 |
|:---|:---|:---|
| **区块 / 页面首次加载** | `<Skeleton>` | 用户**在看一个还没有内容的位置** |
| **按钮操作进行中** | `<Loader2>`（按钮内） | 用户**刚点了一个动作**，在等它完成 |
| 文字型「加载中…」 | **禁止** | 占位没有形状，加载完会跳动 |

⚠️ 这条不写清就会出事：把 65 处 `<Loader2>` 无脑换成 `Skeleton`，**按钮会变成骨架屏**。

**「可撤销」的边界**（与 §2.5 呼应）：`toast` 撤销只适用于**后端真的可逆**的操作。
删除账号当前是硬删除，**没有撤销能力** ⇒ 要么先实现软删除，要么 UI 上**不许出现「已删除·撤销」**。


### 3.7 命令面板（⌘K，加速器）

跨作用域搜账号、跳目的地、执行动作（刷新全部 / 新增账号 / 打开数据目录）。**不替代侧栏**，只作为加速器。这是「顺手」性价比最高的一项。

### 3.8 路由

```
/s/{scope}/{destination}[/{sub}]
例：/s/wb-global/accounts
    /s/trae-cn/usage/tokens
```

- `/` 与 `/trae/*` 全部**重定向**到 `/s/{上次或默认 scope}/*`；`?line=` 解析一次后写入新路由。**旧书签不失效。**
- 上次作用域写入 localStorage，冷启动落到它。
- 收益：刷新 / 前进后退 / 分享链接行为一致；彻底消灭「账号页 state vs 统计页 localStorage」的分裂。

### 3.10 图表规范（九条，改图时必须守住）

可视化最容易出的一类问题不是"难看"，而是**图在撒谎**——数字自相矛盾、或视觉暗示与事实相反。所以定硬规则：

1. **图与表同源**。同一件事的数字只有一个来源：图表一律从数据算，不在渲染层写死任何数字。
   派生数据（按模型的每日序列、时段热力、到期分布…）**全部由已有数据推导**，不新增手写数字。
2. **堆叠柱各分段之和必须精确等于当日总量**（最后一段吃掉舍入余数）。
   否则「堆叠柱总高」与「单色柱高度」对不上，是能被一眼看穿的假数据。
3. **高位小幅波动的序列（如积分余额）基线不锚 0**，并在图注里写明基线值。
   6406→7910 若从 0 起画会被压成一条直线——**视觉上等于在撒谎说「没变」**。
4. **每张图带 `role="img"` + 中文 `aria-label`，每个数据点给 `<title>`**。
   看不了图的人要能拿到同样的信息。
5. **图注不许写废话**。累计曲线的「峰值」就是「末值」，写出来等于没说；
   要么换成「区间累计 / 单日峰值」，要么改成「起 → 止（基线 X）」。

实测中这五条各抓到过真问题：第 2 条保证堆叠柱可信；第 3 条修掉了余额曲线的"假平线"；
第 5 条修掉了累计曲线那句「峰值 2,847,769 · 末值 2,847,769」。

#### ★ 第 6–9 条（v2.1 新增，图表「能用」的门槛）

6. **颜色可辨识，且不靠颜色单独承载信息**。
   序列色板对背景对比度 **≥ 4.5:1**；深浅两主题各自校验（暗色下 `--chart-*` 需重取，不能沿用亮色值）。
   避免红绿相邻作为唯一区分（色盲用户不可辨）——同类图表改用**形状 / 纹理 / 直接标注**做冗余编码。
   ⚠️ 与本仓「涨红跌绿」的既有约定冲突时，**金融类数值**仍按中国习惯（涨红跌绿），
   但**非涨跌语义**的序列（如「按模型」）不许借用红/绿。

7. **数据点过多时必须抽稀或聚合，且告知用户**。
   序列超过 ~120 点时按时间桶聚合（日 → 周），并在图注写明「已按周聚合」；
   不许默默丢点（丢点会让「总量」对不上，违反第 1、2 条）。

8. **图表与表格必须能互切**，且切换后**看到的是同一份数据**。
   每张图右上角给「图 / 表」切换；表视图是图表的**可访问性兜底**，也是「想知道确切数字」时的出口。

9. **图要能被带走**：支持导出当前图为 PNG / SVG（复制到剪贴板或存文件）。
   导出件必须带标题、时间范围、图注与数据来源——**脱离上下文的一张图等于一张假图**。

### 3.11 无障碍规范（v2.1 新增）

v2 初稿只在图表里提了 `role="img"` + `aria-label`，其余交互**全无**无障碍要求。
而原型里手写的 `aria-hidden` 切换层**没有 `aria-modal`、没有焦点陷阱**——键盘用户会被困住或迷失。
以下是**必须项**（不是加分项）：

| 交互件 | 要求 | 落地方式 |
|:---|:---|:---|
| **右侧抽屉**（§3.5） | `role="dialog"` + `aria-modal="true"` + **焦点陷阱** + `Esc` 关闭 + **关闭后焦点归还触发按钮** | 用 Radix `Dialog`/`Sheet`，**不要手写**——这些行为是 Radix 的默认能力，手写必然漏 |
| **命令面板**（§3.7） | combobox 语义 + `aria-activedescendant` + 上下键漫游 + `aria-live` 播报结果数 | 用 `cmdk`（Radix 生态），不要手写列表 |
| **批量操作条**（§3.4） | `role="toolbar"` + 方向键在按钮间移动；结果用 `aria-live="polite"` 播报 | 勾选态变更需播报「已选 N 项」 |
| **勾选框 / 三层会话树** | `role="checkbox"` + `aria-checked`，**半选必须 `aria-checked="mixed"`** | Radix `Checkbox`；手写 `<button class="check">` 会丢掉半选语义 |
| **作用域选择器**（§3.1） | `aria-haspopup="menu"` + 打开后焦点进入菜单 + `Esc` 归还 | Radix `DropdownMenu` |
| **表格视图**（§3.4） | 表头 `aria-sort`；行可选时 `aria-selected` | Radix `Table` |
| **全局** | 焦点可见（`:focus-visible` 环不许 `outline:none` 后不补）；`prefers-reduced-motion` 时禁用过渡动画 | 主题令牌里统一 |

**焦点管理是「全局横切」能力，不是某个组件的局部属性**——它必须进附录 A 的维度表（见附录 A 新增行）。

### 3.12 响应式与窄窗降级（v2.1 新增）

v2 §3.1 用「1200px 窗口」论证了作用域不该平铺，但**没有定义窄窗下的行为**。
而应用 `minWidth: 720`（`tauri.conf.json`），即窗口可以窄到 720px —— 那时 240px 侧栏 + 内容区只剩 480px。

| 断点 | 行为 |
|:---|:---|
| **≥ 1280px** | 完整形态（侧栏 240 + 内容区） |
| **1024–1279px** | 侧栏收窄至 200px；账号卡片从 3 列降为 2 列 |
| **900–1023px** | 侧栏转为**图标栏**（64px，hover/聚焦展开为浮层）；账号列表**强制卡片视图**（表格在此宽度不可读） |
| **< 900px** | 作用域按钮退化为「图标 + 状态点」（隐藏文字）；`ViewParamBar` 允许换行 |

侧栏折叠状态写入 localStorage（与 §3.8 的「上次作用域」同一策略）。

### 3.13 两个搜索入口的分工（v2.1 新增）

v2 §3.4 有「列表搜索（`/` 唤起）」、§3.7 有「命令面板（⌘K）」，但**两者关系未定义** ——
用户会困惑「为什么 ⌘K 能搜到、页内搜不到」，或反过来「搜不到以为没有」。

**明确分工**：

| 入口 | 范围 | 结果 |
|:---|:---|:---|
| **列表搜索**（`/`） | **仅当前作用域**、仅账号 | 就地过滤 `#acct-list`；不跳页 |
| **命令面板**（⌘K） | **跨作用域** + 目的地 + 动作 | 搜到别的作用域的账号时，结果显示「在 `<作用域>` 中」，回车 = **跳到该作用域的账号页并带上 `q`** |

两条必须共享同一个「账号搜索索引」，避免两套匹配规则（否则同一关键词两处结果不一致，是新的静默错误）。

### 3.14 全局备份与恢复（v2.2 新增）

**定位：L0 应用级能力（跨作用域）**，入口 = **设置 → 备份与恢复**（第 9 项子导航，见 §3.9）。
理由：它不隶属于任何一个作用域（§2.1 的 L1 是「全应用唯一」），挂在某个作用域下语义就是错的。

> 现状：只有**账号级**的导入导出（`export-accounts-dialog` / `import-accounts-dialog`，
> 及其 Trae 对应件），一次只能处理**一个作用域的几个账号**，且**不含配置**。
> 换机搬迁时用户要重复 4 次、还搬不走签到/轮换/网关配置。这是本节要补的缺口。

### 3.15 会话工作台（v2.3 新增，第 6 个目的地）

> **★ 能力边界（v2.6 补，2026-10-03 逐文件核实）**：会话能力**不是所有平台都有** ——
> 它是**平台固有能力**（§2.7 的 `capabilities`），**当前只有 WorkBuddy 平台具备**。代码事实：
>
> - 实现绑死 **WorkBuddy 数据三件套**：
>   ① 正文 `~/.workbuddy/projects/{workspace}/{cid}.jsonl`；
>   ② 索引 `~/.workbuddy/workbuddy.db` 的 sessions 表；
>   ③ **云端归属映射** `~/.workbuddy/edge-sync-mapping-v{N}.db`。
> - 第 ③ 件是关键：复制后靠 `register_edge_sync_mapping_for` 把新会话**归属到目标账号**，
>   这是 WorkBuddy 特有的云端同步机制。**Trae 侧没有等价的三件套** ⇒ 复制过去的会话无法归属。
> - 本仓 Trae 模块里**没有任何会话列表 / 复制 / 关联的实现**（命中的 `SessionDead` 是凭据失效错误类型，无关）。
>
> ⚠️ **由此推出两条硬结论**：
>
> 1. **「会话复制」不是加个开关就有的能力** —— 它依赖平台自身的数据布局与云端归属机制。
>    新增平台若要支持，前提是**该平台有等价的三件套**，而不是"实现一下就有了"。
> 2. **Trae 作用域下，会话目的地不应渲染入口**（走 §3.2 的可配置目的地）；
>    若经 URL 直达，给**结构化空态**说明「该平台暂不支持会话管理」，
>    **而不是列出 WorkBuddy 的会话** —— 后者会让用户以为"复制过来了"。
>
> ⚠️ **精确到客户端，不只是平台（v2.6 补）**：会话复制的调用点在 `switch.rs`
> （**WorkBuddy 账号切换路径**）⇒ **CodeBuddy IDE / CLI 也没有这个能力**。
> 所以 §3.15.1 的客户端 Tab **当前只剩「WorkBuddy 桌面」一项**，按下面的退化规则**应不渲染**。
>
> ⚠️ **另需区分「复制」与「关联」**：本仓**当前只有复制、没有关联** ——
> 命令面只有 `list_sessions` / `copy_sessions`（切换时按需复制），
> **没有** session group / 增量同步 / 分歧处理的管理面。
> **本节的「关联会话」是新增能力，不是现状**；实施时不要以为"已经有了、只是没做页面"。

**它解决什么问题**：切换账号时可以把当前账号的会话复制给目标账号。复制过的会话会建立
**跨账号关联**——同一份会话在多个账号里各有一份副本，用户在各自账号里继续用，内容就会**分叉**。

于是需要回答：**哪些会话在哪些账号里有副本、谁落后了、谁分叉了、把谁同步给谁。**

这是**账号工作台装不下的东西**：它不是「某个账号的属性」，而是「账号之间关系」的属性。
v2 初稿把它漏掉了，导致「账号」这一项会被迫承担两套完全不同的心智模型。

#### 3.15.1 信息架构

> ⇒ 客户端只有 1 项 ⇒ 按「单选项的切换器是假控件」退化成静态标题。
> **将来有第二个客户端支持会话复制时，Tab 会自动出现**（下面的规则 1 就是它的规格）。

**三条 IA 规则**：

1. **客户端用「大卡片 Tab」而不是小标签。** 客户端之间有明确语义差异（谁能复制会话、谁要重启），
   小标签塞不下。每个 Tab 显示：图标 + 名称 + **会话组数量**。
   ⚠️ **两个过滤条件，都满足才渲染**：
   ① **具备会话能力**（`capabilities.sessionCopy` —— §2.7 的**平台固有**维度）；
   ② **用户启用**（§2.7 的**用户偏好**维度）。
   全被过滤掉时给结构化空态，但**两种原因要给不同出口**：
   「该平台不支持」→ 说明原因（不引导用户去设置里找开关）；
   「被你自己关掉了」→ 给「去设置」入口。
   ⚠️ **只剩 1 项时不渲染 Tab**（退化成一个静态标题）——
   一个只有单个选项的「切换器」是**假控件**（与 §3.4 规则 1 同源：没有意义的结构不渲染）。
   **本仓当前正好是这种情况**：会话复制只有 WorkBuddy 桌面有 ⇒ **Tab 不该出现**。
   保留 Tab 结构，是为了将来有第二个客户端支持时能**零改动**地出现。
2. **筛选器按需出现**：状态筛选（全部 / 落后 / 分叉 / 已一致）中，
   **没有任何会话组处于该状态的选项不渲染**——避免「点了永远是空」的假选项。
3. **分页阈值隐藏**：少于阈值（约 8 组）不分页，也不显示「显示 1–N，共 M」。
   没有数据的筛选条件与没有意义的分页器，都是**噪声**。

#### 3.15.2 会话关联图（核心可视化）

点开一个会话组 → 右侧抽屉展示**分支图**：同一份会话在各账号中的副本关系。

```
        ┌─ 共同旧版 ────────────┐
        │  2026-09-30 14:22      │
        └───────────┬────────────┘
        ┌───────────┴───────────┐
   ┌────┴─────┐          ┌─────┴──────┐
   │ jackey   │          │ team-shared │
   │ +3 条     │          │ 无更新       │
   │ ← 最新    │          │ 落后 3 条    │
   └──────────┘          └─────────────┘
```

**设计要点**：

- **每个副本必须显示「相对共同旧版」的差异**（+N 条 / 落后 N 条 / 无更新），
  而不是只显示时间戳——**时间新不等于内容新**（可能是另一条分支）。
  这与 §3.10 第 1 条同源：图不能撒谎。
- **分叉时必须标出「共同旧版」**，让用户看得见「从哪开始分的」。
- 选中一份 → 「统一到其他副本」；**有分叉时必须先选保留哪一份**才能统一（不许静默覆盖）。

#### 3.15.3 统一的重启确认流程（跨程序位复用）

切换 CodeBuddy IDE / TraeWork / TraeCode 时，客户端需要**先关闭再打开**。
各客户端各写一套确认弹窗必然漂移 ⇒ 抽成**一条流程**：

```
┌─ 需要重启 CodeBuddy IDE ──────────────────────┐
│ 已检测到 CodeBuddy IDE 正在运行。              │
│ 写入新账号后需要重启它才能生效。                │
│                                               │
│ ☑ 自动关闭并在写入后重新打开                   │
│ ⚠️ 未保存的文件可能丢失，请先保存。             │
│                                               │
│                      [取消]  [继续并重启]      │
└───────────────────────────────────────────────┘
```

⚠️ **CLI 是例外**：切换 CodeBuddy CLI **不重开**客户端，且会**中断当前 CLI 会话** ——
文案不能沿用「自动重开」的措辞（§3.3 规则 2）。

- **默认勾选「自动重开」**（符合预期），但**必须显式提示未保存文件的风险**。
- **CodeBuddy CLI 不走这条流程**：它的切换会**中断当前会话且不自动重开**，
  文案要如实说明（「当前 CLI 会话会中断」），**不能沿用「自动重开」的措辞**——
  这是「错误预防」：让用户在按下去之前就知道代价。
- 切换完成后 toast 给明确结果：「已重启」/「未重启，需手动启动」。

#### 3.15.4 批量同步与部分失败

「同步安全项」（把落后但未分叉的副本一次补齐）是**批量写操作**，必须走 §3.6 的部分失败态：
汇总条 `N 成功 / M 失败` + 「重试失败项」+ 可展开明细。

**同步是加法**：只把来源的新增内容追加到目标，**不删除目标已有的任何内容**。
UI 文案要显式写出这一点——用户对「同步」的最大恐惧就是被覆盖。

### 3.16 桌面悬浮窗（v2.3 新增，**独立能力；D21 已拍板：进本期**）

**它解决什么问题**：用户在多个 AI Agent 客户端（桌面版 / CLI / IDE 插件）里同时跑任务，
**没有一个地方能一眼看出「谁还在跑、谁在等我确认、谁已经完成」**——必须逐个切窗口看。

**形态**：一个**可拖动的桌面浮层**，列出各来源的会话状态；悬停出信息卡；点击**回到原会话**；托盘可临时隐藏。

**这是本应用里唯一一个「常驻桌面、脱离主窗口」的 UI**，所以必须单独定规则：

| 项 | 规则 |
|:---|:---|
| 层级 | **不属于 L0–L3**。它是**独立浮层**，有自己的窗口；主窗口关闭后是否存活由用户设置决定 |
| 入口 | 侧栏左下角图标 + 设置页开关（走 §2.7 的**用户偏好**，不是 `capabilities`） |
| 数据 | **只读**订阅各来源状态；**不承载任何写操作** |
| 状态 | 运行中 / 待确认 / 已完成 / 失败（与 §3.6 的状态语言对齐） |
| 交互 | 拖动改位置；悬停出卡；点击跳转；托盘显示 / 隐藏 |
| 无障碍 | 独立窗口 ⇒ **键盘可达性要单独验证**（不能假定主窗口的焦点管理适用） |
| 隐私 | 浮层默认**不显示完整会话标题**，悬停才展开（与 §3.3 的邮箱脱敏同一原则：防截图泄露） |

⚠️ **明确不做的**：不在浮层里做账号切换、不做批量操作、不做自定义布局编辑器。
浮层的价值是「一眼看清 + 一键回去」，往里加东西就毁掉这个价值。

> **与重构主线的关系（D21 已拍板：进本期）**：悬浮窗是**独立产品能力**，与「作用域 / 工作台 / 注册表」
> 这套重构**互不依赖** ⇒ **P9 与 P0–P8 解耦**（除注册表外不共享代码），并**排在 P8 之后启动**，
> 避免两条复杂线同时进行、出问题时难以归因。
> 它在 IA 上占**第 7 个「目的地级」入口**，但**不占侧栏项**（入口在侧栏左下角 / 托盘）。

### 3.17 网关接入与模型自动识别（v2.4 新增）

**它解决什么问题**：网关对外提供 `/v1/models`，接入方（编辑器插件、各类 SDK）会**自动发现**可用模型。
但这条链路上有**两个断点**，任何一端断了，「自动」就变成「手填」：

| 断点 | 现状 | 后果 |
|:---|:---|:---|
| **上游 → 我们** | 模型清单**要用户手动点刷新**；不点就用「内置兜底清单」 | 用户接入后看到一份**不知道准不准**的列表 |
| **我们 → 客户端** | 接入指引只给了 Base URL + Key，**没说「模型会被自动发现」** | 用户以为要手填模型名，白折腾 |

**核心主张**：**接入即识别，识别即可发现。**

- 上游 → 我们：绑定凭据成功后**自动探测**模型清单；
- 我们 → 客户端：`/v1/models` 让客户端**自动列出**模型，无需手填。

#### 3.17.1 三级来源（已有机制，这里强化为契约）

| 来源 | 含义 | 出现时机 |
|:---|:---|:---|
| **实时** | 本次从上游成功拉到 | 探测成功 |
| **已保存** | 上次成功的结果，本次没拉到 | 探测失败但有缓存 |
| **内置** | 从未成功过，用内置兜底 | 首次或一直失败 |

**三条硬规则**：

1. **三级必须显式标注**（徽标 + 时间 + **失败原因**）。**不许把「内置」伪装成「实时」**——
   用户照着清单去调用、结果模型不存在，是典型的**静默错误**（§3.6）。
2. **对外的 `/v1/models` 必须与我们识别的清单同源**。这是本仓既有硬约束：
   若客户端自动发现到的模型名与实际可调的不一致，用户会判定「网关坏了」。
3. **识别失败不阻断接入**。接入成功 + 识别失败 = 「**可用但清单待确认**」，
   给「重试 / 稍后再说」出口，**不把接入本身也标成失败**。

#### 3.17.2 触发时机（四个）

| 时机 | 行为 |
|:---|:---|
| **新绑定 API Key / OAuth 登录成功** | **立即探测** —— 这是「接入即识别」的落点 |
| 网关启动 | 清单为「内置」或已过期（> 24h）→ 后台探测 |
| 切换作用域 | 该作用域清单待确认 → 后台探测 |
| 手动刷新 | **保留**（兜底，不做成唯一入口） |

探测**单次超时短（约 8s）、失败后台重试、不弹模态阻塞用户**。
（与 §3.1 的 macOS 避让、§3.12 的响应式同属「不能因为后台动作打断用户」这一类。）

#### 3.17.3 ★ 三个陷阱（不处理的话，「识别」会骗人）

1. **识别到的 ≠ 能用的。** 上游下发的清单可能含**不可服务**的条目——本仓 Trae 侧已有这层过滤
   （`servable_entries`）。⇒ UI 只展示**过滤后**的清单；原始清单只进诊断，不给用户看。
2. **名称必须按区域规范化。** 同一模型在国际版是**裸名**、在国内版带 **`CN` 后缀**。
   ⇒ 识别必须**按 scope 分家**，并把名称规范化到该 scope 的形态。
   否则用户从 `/v1/models` 复制名字去调用会失败——而他会以为是网关的锅。
3. **「HTTP 200」不等于「模型可用」。** 有的上游把错误放在响应体 / SSE 里
   （本仓 Trae 侧就有「失败也是 HTTP 200，错误在 `event:error`」的既有事实）。
   ⇒ **不做校验时，文案只能说「已识别 N 个模型」，不能说「N 个模型可用」。**
   措辞差一个词，承诺就完全不同。

#### 3.17.4 UI

**接入向导的最后一步新增「识别」阶段**：

```
┌─ 接入完成 ──────────────────────────────────────┐
│ ✓ 凭据已保存                                     │
│                                                 │
│ ⟳ 正在识别可用模型…                              │
│  ── 成功后 ──                                   │
│ ✓ 已识别 12 个模型                               │
│   来源：实时 · 2026-10-03 12:48                  │
│   ⚠️ 已识别 ≠ 已校验，首次调用请留意错误           │
│                                                 │
│                [查看模型清单]   [完成]            │
└─────────────────────────────────────────────────┘
```

失败态（**不阻断**，且**说清回落到了什么**）：

```
│ ⚠️ 未能识别模型清单（上游未响应）                  │
│    已回落内置清单，可能过时。                      │
│                [重试]   [稍后再说]                │
```

**模型清单页**：

- 来源徽标（实时 / 已保存 / 内置）+ **上次识别时间**（相对时间，悬停给绝对时间）；
- 来源**不是「实时」时必须显示原因**（不能只给一个灰色徽标——用户不知道是"正在加载"还是"拉不到"）；
- 刷新按钮；
- **按 scope 分组的 Tab**（国内版 / 国际版清单不同，由 §2.3 的注册表驱动，不是硬编码两套）。

**接入指引卡片**（现有「快速接入」）要补一句：

> 客户端会自动从 `/v1/models` 读取模型清单，**不需要手填模型名**；
> 若你的工具不支持自动发现，从「模型」页复制即可。

#### 3.17.5 与安全边界的关系（§2.5）

- 探测请求**必须使用该 scope 自己的凭据**，**禁止跨 scope**（否则会把 A 的清单写到 B）。
- 探测失败**不许静默回落到另一个 scope 的缓存**——宁可显示「内置」。

### 3.18 模型禁用与接入说明（v2.5 新增）

#### 3.18.1 模型禁用

**需求**：把某些模型**从网关的可用清单里拿掉**。

**典型场景**：① 不想让接入的工具误用高消耗模型（opus 留给手工用）；
② 上游清单里有测试 / 内部模型，不该暴露给接入方；③ 某模型当前报错率高，先禁掉止血。

**★ 与「可用性」是两个正交维度**（本节最重要的一条）：

| 字段 | 谁决定 | 含义 |
|:---|:---|:---|
| `available` | **上游** | 这个模型**事实上**能不能调 |
| `disabled` | **用户** | 用户**主动**把它从可用清单里拿掉 |

四种组合都合法，UI 必须能表达：

| available | disabled | 展示 |
|:---|:---|:---|
| ✓ | ✗ | 可用 |
| ✓ | ✓ | **已禁用**（上游可用，但用户禁了） |
| ✗ | ✗ | 上游不可用 |
| ✗ | ✓ | 已禁用（且上游也不可用）—— 合并展示即可 |

**⚠️ 两个出口必须同时改，否则「禁用」是假开关**：

1. **`/v1/models` 不再列出被禁用的模型** —— 这是禁用的**主要意义**（接入方自动发现时看不到它）；
2. **直接用被禁用的模型名调用 → 返回明确错误**，且错误信息**必须说明是「被禁用」**，
   而不是笼统的 4xx —— 否则用户会以为网关坏了。

> 只改第 1 条 = **假开关**（隐藏了但调得通）；只改第 2 条 = **用户困惑**（清单里有、调了报错）。
> **两条一起改才叫「禁用」。** 这与 §3.17 的「识别到的 ≠ 能用的」是同一类问题的两个方向。

**粒度与归属**：按 **scope** 禁用（不同 scope 的清单本就不同）；
它是**用户偏好**（§2.7），存本地配置，**不进 `capabilities`**。

**复用既有拒绝路径**：网关已有「模型前缀路由 + 拒绝并给说明」的机制（跨区域调用会被拒）。
禁用模型应当**走同一条拒绝路径**，**不要新造一套错误格式**——否则客户端要处理两套错误。

#### 3.18.2 `/v1/messages`（Anthropic 兼容）—— **已支持，不需要新增开发**

**结论：这一条是「告知」问题，不是「实现」问题。** 代码事实：

- `POST /v1/messages` **已挂载**，**WB 侧与 Trae 侧都有**；
- 支持**流式与非流式**（按请求体的 `stream` 字段分流）；
- 支持 Anthropic SSE 聚合、模型名重写、用量统计。

**认证方式**（最容易踩的细节）：网关**同时接受**两种头——

- `x-api-key: <Key>` —— Anthropic 系客户端的默认方式；
- `Authorization: Bearer <Key>` —— OpenAI 系客户端的默认方式。

⇒ 接入说明里**必须按客户端分别写清楚用哪个头**，否则用户会拿着 Anthropic 客户端去填 Bearer。

#### 3.18.3 接入说明（按协议 + 按工具）

**信息架构**：接入说明从「一个 curl 片段」升级为**两段式**：

1. **协议 Tab**（OpenAI 兼容 / Anthropic 兼容）—— 决定端点路径、认证头；
2. **工具 Tab**（该协议下已知的工具）—— 决定「填到哪个配置项」。

**通用参数**（所有工具都要）：

| 参数 | 值 |
|:---|:---|
| Base URL | `http://127.0.0.1:<端口>` |
| API Key | 「密钥」页创建（明文只展示一次） |
| 模型名 | **不用手填** —— 客户端从 `/v1/models` 自动发现（§3.17） |

**按协议的差异**：

| | OpenAI 兼容 | Anthropic 兼容 |
|:---|:---|:---|
| 端点 | `POST /v1/chat/completions` | `POST /v1/messages` |
| 认证头 | `Authorization: Bearer <Key>` | `x-api-key: <Key>`（网关也接受 Bearer） |
| 模型发现 | `GET /v1/models` | 同左 |

**按工具**（只列**已确认**的；未确认的一律归入「其它 OpenAI / Anthropic 兼容工具」）：

| 工具 | 协议 | 要填什么 |
|:---|:---|:---|
| Claude Code | Anthropic | `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` |
| Codex | OpenAI | 自定义 `model_provider`：`base_url` + `env_key` |
| opencode | OpenAI / Anthropic 均可 | provider 配置里的 baseURL + apiKey |
| 其它（DeepSeek Harness / OpenClaw / Agent Harness 等） | 按各自协议归入上表两列 | **给通用参数即可**；具体配置文件位置**以该工具官方文档为准** |

> ⚠️ **诚实边界**：接入说明**只写能确认的**。对不确定的客户端，给「协议 + 通用参数 + 一句『以其官方文档为准』」，
> **不编造配置片段** —— 编错的配置比没有说明更糟（用户会以为网关坏了）。
> 与 §3.10 第 1 条同源：**不许在渲染层写死或编造内容**。

### 3.19 请求代理与无缝切号（v2.7 新增，P12）

**需求**：网关不只代理 LLM 调用，而是**代理客户端自身的业务请求**，
由网关侧决定「这次请求用哪个账号」⇒ **动态无缝切号**（不写文件、不重启客户端）。

#### 3.19.1 为什么现在的切换是「重」的

现状：切换 = **改客户端的登录态存储**（`auth_file` / `state.vscdb` / `storage.json`）+ **关闭并重开客户端**。
⇒ 必然中断当前工作；而且客户端把 token 缓存在**内存**里，改了文件也得重启才生效。

**要「无缝」，只有一条路：让请求经过一个能换凭据的中间层。**

#### 3.19.2 可行性核实（逐文件，2026-10-03）

**① 上游域名**（决定代理范围）：

| 平台 | 区域 | API 域 | 网页域 |
|:---|:---|:---|:---|
| WorkBuddy | CN | `https://www.codebuddy.cn` | `https://www.workbuddy.cn` |
| WorkBuddy | Global | `https://www.workbuddy.ai` | 同左 |
| Trae | CN | `https://api.trae.cn` | `https://www.trae.cn` |
| Trae | Global | — | `https://www.trae.ai` |

（另有 `https://api.trae.com.cn` = icube 主机）

**② 凭据形态**（决定「能不能换」）：

| 平台 | 认证 | 能否单纯替换 |
|:---|:---|:---|
| WorkBuddy | `Authorization: Bearer <token>`（`credits.rs::authenticated_post_for` → `post_with_account`），**无签名** | ✅ 直接换 token |
| Trae | Bearer + **P-256 ECDSA 设备证明签名**（`trae/icube.rs` 的 `device_proof_signature`） | ⚠️ 换 token 后**签名必须重做**；**本仓已实现该签名** ⇒ 可行 |

⇒ **凭据层面两个平台都可行**（WB 直接换；Trae 复用现成签名实现）。

**③ 真正的 go/no-go：TLS 中间人**

客户端访问的是 `https://` ⇒ 网关要当中间人，**必须让客户端信任一个自签 CA**。
**若客户端做了证书固定（certificate pinning），方案直接不成立** —— 这不是工作量问题，是**硬阻塞**。

⚠️ **所以 P12 的第一步不是写代码，而是做一个可行性 spike**：
装自签 CA → 看客户端是否报证书错误。**spike 失败则整个 P12 作废**
（**不要先写代码再发现走不通** —— 这正是 §3.17「先量化再投入」的同源纪律）。

#### 3.19.3 拦截方式：三条路，代价差很多

**要让客户端把请求发到网关**，有三条路：

| 方式 | 做法 | 代价 | 取舍 |
|:---|:---|:---|:---|
| **A. 客户端 / 系统 HTTP 代理** | 客户端支持 `--proxy-server`（Electron）或 `http.proxy`（VS Code 系）⇒ 指向网关 | 仍需 TLS 中间人；但**代理范围可控**（只代理白名单域，其余直连） | ✅ 候选（**客户端主动委托**） |
| ~~**B. hosts + 本地 TLS**~~ | 改 hosts 把域名指到 `127.0.0.1` ⇒ 网关提供该域名的自签证书 | 需管理员权限；**影响全机**，其他程序访问同域名也被劫持 | ❌ **已排除（2026-10-03 拍板：不劫持）** |
| **C. 客户端自定义服务端地址** | 若客户端支持配 base URL ⇒ 直接指向网关，**无需中间人** | 取决于客户端是否支持；且**大概率只对 LLM 调用有效**（见 §3.19.10 D） | ✅ 候选（**最干净，连 CA 都不用**） |

**★「不劫持」的明确定义（2026-10-03 拍板）**：

- **不改 hosts**、**不做 DNS 劫持**、**不做透明代理**；
- 只允许**客户端主动把请求交给网关**（A：客户端配代理；C：客户端配 base URL）。

⚠️ **代价必须写清**：排除 B 之后**没有兜底** ⇒ **A / C 都不可行时，P12 直接作废**。
这是**有意接受的取舍**：**宁可功能做不成，也不动用户的系统解析** ——
因为改 hosts 影响全机、杀软会报警、卸载不干净就是长期隐患，
而一个"账号切换工具"去劫持系统解析，**信任成本远高于功能收益**。

⚠️ **一个待确认的分界点**：**A 需要 CA 才能改 HTTPS 内容**（否则只能看到 CONNECT，改不了凭据）。
它是「客户端主动走代理 + 用户显式信任 CA」，**不是劫持**；
但**若「中间人解密」也被视为不可接受**，则 A 也要排除 ⇒ **只剩 C** ⇒
而 C 大概率覆盖不到业务请求 ⇒ **P12 作废**。这一点需要明确（见 D33）。

⚠️ **待调研（P12 前置）**：WorkBuddy（Electron）与 Trae（VS Code 系）分别支持哪种？
Electron 系通常认 `--proxy-server` 与系统代理；VS Code 系有 `http.proxy` 设置项。
**这项调研与证书固定 spike 一起做**，同属 go/no-go。

#### 3.19.4 代理范围：只碰白名单域名

**绝不代理全部流量。** 白名单 = §3.19.2 ① 表里的域（+ 必要的 CDN / 静态域，若客户端把它们也走代理）。

三条硬规则：

1. **白名单外一律直连**（不解析、不记录、不缓存）；
2. **不落盘请求体 / 响应体**（内存转发；日志只记元数据：时间、域、路径、状态、耗时、账号）；
3. **明文 HTTP 不代理**（避免沦为任意流量的透明代理）。

⚠️ 与 §3.14 备份的「凭据开关」同源：**能力越大，默认越保守**。

#### 3.19.5 选号：复用现有池，不新造一套

**选号必须复用现有的账号池内核**（`pool/entry_like.rs::PoolEntryLike` + `PickPolicy`），
**不要为代理另写一套** —— 否则「选哪个账号」会有两份实现，策略必然漂移。

- **按请求选号**（默认）：每次业务请求独立选号 ⇒ 真正"动态"；
- **粘性**：同一会话 / 同一时间窗内保持同一账号（复用 `StickyTable`）——
  否则用户会看到「积分一会儿这个数一会儿那个数」；
- **显式指定**优先于自动择优（与现有优先级一致：**显式 > 粘性 > 自动**）。

⚠️ **两个必须排除的候选**：**已用完 / 已过期**的包 —— 与 issue #7 同源
（空包会把紧迫度顶满，导致真正快过期的账号永远轮不到）。

⚠️ **与 WorkBuddy 行为基线的冲突**：`PickPolicy` 的默认值（`expiry_urgency_weight = 0`、
`deterministic = false`）是 **WorkBuddy 的选号基线**。代理链路若要用不同默认值，
**必须走 `trae_pick_policy()` 那样的显式覆写**，**不许改默认值**（改默认值会静默改 WorkBuddy 的选号）。

#### 3.19.6 失败处理：401 换号重试，这才是「无缝」的价值

| 上游响应 | 处理 |
|:---|:---|
| `401` / 凭据失效 | **换一个账号重试一次**（无缝切号的核心价值）；仍失败 ⇒ **原样返回，不吞错误** |
| `429` / 限流 | 标记该账号短冷却（复用 `credits.rs` 的冷却机制），换号重试 |
| `5xx` | **不换号**（上游故障，换号无用），原样返回 |
| 网络错误 | 不换号，原样返回 |

⚠️ **换号重试必须幂等安全**：只对**读操作**自动重试；
**写操作**（签到、领取、提交）**不自动换号重试** —— 否则可能**重复执行**（领两次奖励）。

**判据**：按方法与路径维护一张「可重试」白名单，**默认不可重试**（fail-closed）。
这与 §2.5 的「scope 解析 fail-closed」是同一条纪律：**拿不准就不做，而不是猜。**

⚠️ **重试次数上限 = 1**（换一个号，不是无限轮转）。无限重试会在所有账号都失效时变成风暴，
且用户看到的是"卡住"而不是"失败"。

#### 3.19.7 安全边界：这是本项目**权限最大**的功能，必须默认关

代理客户端请求意味着 **网关能看到客户端的全部业务流量**（含账号身份）。
这是本项目迄今**权限最大**的能力 ⇒ 安全要求必须高于其他所有功能：

1. **★ 绝不劫持**（2026-10-03 拍板）：**不改 hosts / 不做 DNS 劫持 / 不做透明代理** ——
   只接受**客户端主动把请求交给网关**（A 配代理 / C 配 base URL）。
   ⇒ **A / C 都不可行时宁可不做**（代价见 §3.19.3）。
2. **默认关**；开启时必须**逐条列出**将要代理的域名，并说明「流量会经过本机网关」；
3. **自签 CA 必须由用户显式安装**，且**给出卸载入口**（一键移除证书与代理设置）；
4. **不落盘正文**（§3.19.4 规则 2）；
5. **请求日志默认脱敏路径中的 id**（与 §3.3 的邮箱脱敏同源）；
6. **关闭时彻底还原**：撤代理设置 / 提示移除 CA —— **不留残留**。

⚠️ **必须有「一键还原」**：用户试了不满意要能干净地回到原状。
这也是 §3.14 备份「导入前自动快照」的同源思路：**给出路，才敢让人试**。

#### 3.19.8 与现有能力的关系（别重复造）

| 已有能力 | 与 P12 的关系 |
|:---|:---|
| 账号池 + `PickPolicy` | **直接复用**（§3.19.5），不新写 |
| 冷却机制（`credits.rs`） | **直接复用**（429 处理） |
| 网关请求日志（`request-log.tsx`） | **扩展**：加「代理」来源标记，不另起一套 |
| 网关的 Key 体系 | **不复用** —— 代理链路用的是**账号凭据**，与网关 Key 是两套东西，**别混** |
| 会话复制（§3.15） | **无关** —— 那是文件层，这是网络层 |

⚠️ **最后一条最容易搞混**：P12 让「切号」变快，**但不解决「会话跟着走」** ——
会话复制仍然依赖数据三件套（§3.15 能力边界）。**两件事都要做，不能互相替代。**

#### 3.19.9 分期：先 spike，再最小可用，最后才谈策略

**P12 拆成三步，前一步失败就不进下一步**（避免投入沉没）：

| 步 | 内容 | 通过判据 |
|:---|:---|:---|
| **P12a（spike）** | **步骤 0 先查 C**（业务域能否配自定义地址）→ 步骤 1 只配代理不装 CA → 步骤 2 装 CA 探证书固定 | **至少一条路可用（A 或 C）**；走 A 还需**不报证书错误**（无 pinning） |
| **P12b（C 路，先行）** | 改客户端 base URL 指向网关 + 单账号（不选号） | **AI 调用**正常切号；**无需 CA、不碰 TLS** |
| **P12c（A 路，后评估）** | 只代理一个白名单域 + 单账号 + 读操作直通 → 再上选号 + 粘性 + 重试 + 日志 + 一键还原 | 业务请求正常；**A 是否值得做，在 P12b 之后重新评估**（见 D34） |

⚠️ **顺序是 C 先行，不是 A 先行**（D34）：
C 覆盖**高频的 LLM 调用**且**不需要 CA**；A 覆盖的是**低频的业务请求**却成本最高
（本仓的签到 / 积分是它自己直接调上游的，**不经过客户端**）。

⚠️ **P12a 不通过就停在 P12a**，并把结论写回本节（**失败的 spike 也是产出**：
它省掉了后面两步的全部投入）。

#### 3.19.10 参考实现与可借鉴的做法

> ⚠️ **本节是用户明确要求收录的**（2026-10-03）。按项目约定，外部参考**默认不写进仓库**；
> 本节是**唯一例外**，且**只记可借鉴的技术做法**，不作为"照抄某项目"的依据。

**A. TLS 中间人框架：`mitmproxy`**

它证明了「中间人 + 按请求改写凭据 + 转发」是**成熟模式**，不是本项目独创：

- 首次运行**自动生成 CA**（`~/.mitmproxy/mitmproxy-ca-cert.pem`），客户端需信任它；
- addon 用 `request(flow)` 钩子**改写 header / 选上游**，`response(flow)` 钩子做校验与降级；
- `--ssl-insecure` 跳过的是**上游**证书校验（不是客户端那一侧）。

⚠️ **它文档里的安全警告值得原样搬进我们的开启流程**：
「A trusted mitmproxy CA can decrypt **any** HTTPS traffic that passes through it」⇒
**只在你能控制的设备 / 环境上信任该 CA**。这直接支撑 §3.19.7 的「默认关 + 用户显式安装 + 一键还原」。

**B. 三条可直接落地的做法**

| 做法 | 别人的形态 | 我们怎么用 |
|:---|:---|:---|
| **粘性用「租约」而不是「会话」** | header 携带 session key + `lease_seconds`（如 120s），到期即释放 | 对应 **D31 粘性窗口** —— 比"按会话"更好实现（无需跟踪会话生命周期） |
| **只把「连接失败」当上游故障** | 「A 5xx from the origin is **not** proof the proxy itself is broken ⇒ only a real connect failure cools the upstream」 | **印证 §3.19.6 的「5xx 不换号」** —— 这是别人踩过的坑，不是我们拍脑袋 |
| **按域过滤，只代理匹配的请求** | addon 里 `if "<domain>" in flow.request.host` 才代理，其余 `return None` | **印证 §3.19.4 的「白名单」** —— 说明"过滤"是这类工具的**标配**，不是可选优化 |

**C. 同类工具的两种路线（这决定我们的定位）**

| 路线 | 做法 | 代价 |
|:---|:---|:---|
| **配置切换类**（`cc-switch` 这类桌面工具：管理 Claude Code / Codex 多套配置，"切供应商像切 Wi-Fi"） | 改**客户端配置文件** + 提示重启 | 就是本项目**现状**的做法 —— **"重"**，切换必然中断工作 |
| **代理轮换类**（`TeamClaude`：多账户 Claude 代理 + **自动配额轮换** + 模型感知路由 + TUI） | 客户端指向代理，代理按配额选号 | **无缝**；但要过 TLS / 证书固定，且**代理能看到全部流量** |

⇒ **P12 属于第二条路线**，但比通用工具多两层约束：
① **多平台**（WB + Trae，凭据形态不同）；② **不碰客户端文件**（只做网络层，避免与现有切换链路冲突）。

⚠️ **但有一条本质差别必须说清**：这类工具代理的是 **LLM 调用**（有公开 API 规范），
而 P12 要代理的是**客户端私有的业务请求**（签到 / 积分 / 旅行）——
**后者没有公开规范，协议只能靠本仓已有的逆向成果**（这正是 §3.19.2 ② 表存在的意义）。

⇒ **「有开源项目做过」不等于「我们能照抄」**：能借鉴的是**代理层的做法**，
**协议层必须用本仓自己的实现**。

**D. `cc-switch`（Rust + Tauri + TS，与本仓同栈）：也有代理，但走的是另一条路**

它支持 8 款 AI 编码工具，**内建本地 HTTP 代理**（Axum 监听 `127.0.0.1:15721`，**默认不启动**）。
接管方式值得注意：

- **改 `~/.claude/settings.json`，把 `ANTHROPIC_BASE_URL` 指向本地代理** ⇒ 即 §3.19.3 的 **C 方案**；
- **因此它不需要 TLS 中间人、不需要 CA** —— 流量是 **HTTP 明文**（客户端主动发往 `http://127.0.0.1:...`）。

⇒ **这印证了一件事：C 方案确实可行，但只对「base URL 可配」的流量有效。**
cc-switch 能改的只有 **LLM API 的 base URL** ⇒ **它接管的只有 LLM 调用**，
**碰不到业务请求**（签到 / 积分那些域是硬编码的）。

⚠️ **对本仓的直接结论**：P12 的目标是**业务请求** ⇒
**C 方案对本仓大概率不适用**（除非实测出业务域也可配）——**这正是 §3.19.11 步骤 1 要验证的事**。

**但它有 5 条工程做法非常值得抄（都是别人踩过的坑）**：

| 做法 | 它怎么做的 | 我们为什么需要 |
|:---|:---|:---|
| **保留 header 原始大小写** | 手写 hyper 接收循环 + `preserve_header_case(true)`，原始大小写存进扩展再转发 —— 因为框架默认小写化，`anthropic-version` 变成 `Anthropic-Version` 就 **401** | ⚠️ **真实踩过的坑**：我们的转发层若用现成框架，**必须先验证 header casing 不被改写** |
| **熔断器三态机** | CLOSED / OPEN / HALF_OPEN；`failure_threshold=4`、`success_threshold=2`、`timeout=60s`、`error_rate=0.6`、`min_requests=10`；**状态键 = `app_type:provider_id`** | 比 §3.19.6 简化的「短冷却」更完整；**状态键按（平台, 账号）分家**这条尤其对（本仓是多平台） |
| **所有权 sentinel** | 用**专属 ID**（而非通用 `localhost:15721`）标记「这是我们的代理」，避免把用户**自己指向 localhost 的配置**误当成被接管 | ⚠️ 本仓同样要防：用户可能自己配了别的本地代理 |
| **切换去重** | `pending_switches: HashSet` 写锁占位，避免**并发请求重复触发切换** | 对应 §3.19.6 的换号重试 —— 并发下会重复切 |
| **原子写入** | `atomic_write`（tmp + rename），防写入中途崩溃留半成品 | 与本仓既有的配置文件写入纪律一致 |

**它的 6 层架构**（UI → Tauri Command → Service → Domain → Adapter → Storage）与本仓相近；
其 **Profile = (Provider + MCP + Skills + Prompt) 快照、按 scope 分组**的设计，
与本仓 §3.1「各作用域指向自己的当前档案」**思路一致**（可互相印证）。

⚠️ **一条本质差别**：cc-switch 的代理**不碰 TLS**（改 base URL ⇒ HTTP 明文），
而 P12 要代理**业务请求**（域不可配）⇒ **必须过 TLS 中间人** ⇒
**证书固定这道坎绕不开**。这**强化了 §3.19.11 的 spike 必要性**，而不是削弱它。

#### 3.19.11 P12a spike 的可执行步骤（go / no-go 判定）

**目标**：用最小代价回答两个问题 —— ① 客户端是否拒绝自签 CA（pinning）？② 哪种拦截方式可用？

| # | 做什么 | 通过判据 | 失败含义 |
|:--|:---|:---|:---|
| **0** | **先查 C**（最便宜）：客户端是否允许把**业务域**配成自定义地址 | 业务域可配 | 不可配 ⇒ **C 出局**（**大概率如此**，见 §3.19.10 D） |
| **1** | **只配代理、不装 CA**：客户端指向本地 HTTP 代理（仅记录 CONNECT） | 能看到目标域的 CONNECT 请求 | 客户端**不认代理** ⇒ **A 出局** |
| **2** | **装 CA + 中间人**：信任自签 CA 后重放步骤 1 | **客户端不报证书错误**，且业务功能正常 | **证书固定** ⇒ **A 出局** |
| **3** | **A 路确认**：认代理且无 pinning ⇒ A 可用 | 业务请求（如看积分）正常，且流量确实过网关 | ✅ **用 A** |
| — | ~~B 路~~ | — | ❌ **已排除（不劫持）** ⇒ **A / C 都出局就是 P12 作废，没有兜底** |

⚠️ **步骤 0 排最前**：它最便宜（只是翻客户端的配置项），且能**直接判死 C** ——
先做它，可以避免为一堆不可行的路浪费时间。

⚠️ **步骤 1 与 2 的顺序不能反**：先确认「客户端认代理」再装 CA ——
否则装完 CA 才发现客户端压根不走代理，**CA 白装还得清理**。

⚠️ **每一步都必须能干净撤销**：代理设置改回、CA 移除。
**spike 阶段就要把「还原」做出来**，不要留到最后（否则试错会把机器搞脏）。

⚠️ **结论必须写回本节**（无论通过与否）：通过的写「用哪条路 + 证据」；
失败的写「卡在哪一步 + 现象」—— **失败的 spike 也是产出**（它省掉后面全部投入）。

#### 网关宿主泛化的**硬约束**

初稿说「网关宿主泛化为 `GatewayHost<Product>`」。注意 `trae_gateway_host.rs:3` 的注释：
两者**平行且有意不复用**，因为 axum 对同一路径 `merge` 两个 router 会 **panic**。
泛化时必须处理这一点（例如按平台各持一个 router、在**不同挂载前缀**下 merge，或显式声明路径所有权），
**不能简单合并成一个结构体**——否则运行期直接崩。

> 3. **★ 「5:5 合并」不是普遍可行的（实测后回写）**：逐对比对子组件后结论**分三类** ——

### 怎么证明它不是「看起来能用」

原型自带**两套** jsdom 验收，分工不同，都要跑：

| 套件 | 守什么 | 断言数 |
|:---|:---|:---|
| `verify-demo.cjs` | **契约**：骨架、导航、搜索/IME、能力开关、命令面板、抽屉向导流程 | 36 |
| `verify-behaviors.cjs` | **行为**：数据自洽、真实聚合、错误态与重试、部分失败、会话树计数、能力门控、账号池排他、程序位多对多绑定、权限自愈点击、**图表完整性与形状**、按作用域取值 | 59 |

```bash
export NODE_PATH="<managed node workspace>/node_modules"   # 需要 jsdom（装在隔离工作区，别往项目里装）

node docs/redesign/verify-demo.cjs         # 36 passed / 0 failed
node docs/redesign/verify-behaviors.cjs    # 59 passed / 0 failed

# 变异注入：把缺陷塞回去，**期望测试变红**。全绿说明断言在空转。
node docs/redesign/verify-demo.cjs      --mutate=boot        # 去掉启动渲染（白屏）
node docs/redesign/verify-demo.cjs      --mutate=cap         # 忽略能力开关
node docs/redesign/verify-demo.cjs      --mutate=ime         # 搜索整页重绘
node docs/redesign/verify-behaviors.cjs --mutate=merge       # merge 退回假开关
node docs/redesign/verify-behaviors.cjs --mutate=snapshot    # 去掉快照能力门控
node docs/redesign/verify-behaviors.cjs --mutate=selectall   # 退回「全选需点两次」缺陷
node docs/redesign/verify-behaviors.cjs --mutate=permretry   # 权限重试退回死按钮
node docs/redesign/verify-behaviors.cjs --mutate=progbind    # 退回单绑定模型
node docs/redesign/verify-behaviors.cjs --mutate=packs       # 资源包名不去重
node docs/redesign/verify-behaviors.cjs --mutate=chartsegs   # 堆叠柱只画一段（图与数据打架）
node docs/redesign/verify-behaviors.cjs --mutate=mergeext    # 合并只影响 days、不聚合图表
node docs/redesign/verify-behaviors.cjs --mutate=baselinen0  # 余额曲线退回锚 0（波动被压平）
```

十二个变异**各自精确打红对应的那几条**，其余仍绿 —— 这就是「断言不是恒真的」的证据。

⚠️ 变异加载器做锚点匹配时**必须先把换行符归一**：本仓文件是 CRLF，而锚点字面量里的 `\n` 是 LF，
直接 `includes` 会**静默不匹配** ⇒ 变异没注入 ⇒ 却因别的原因变红 ⇒ 假验证。
（真踩到过：`progbind` 因此失效一次，靠「锚点不匹配必须报错退出」这条才暴露。）

变异只写 `os.tmpdir()` 里的**副本**，`docs/redesign/` 下的原文件永不被写，
因此不存在「还原后忘记校验哈希」这类风险。

### ★ 一个真实教训：通过的断言，在你证明它会红之前什么都不能说明

`permretry` 这个变异第一次写出来时是**打不红的**，两个原因叠在一起：

1. **变异打错了位置**。原缺陷的成因是「渲染端只传一个参数、处理器却读第二个」。
   我第一次把变异加在**渲染端**（多带一个尾参）—— 而处理器读的是第一个参数，
   尾参不影响它 ⇒ 缺陷根本没被复现。
2. **断言本身是恒真的**。我用 `a1` 做被测账号，而 `a1` **本来就绑着** workbuddy，
   所以「切换后仍绑着」这句永远成立。换成初始未绑任何程序位的 `a3` 之后，
   「切换后绑上了」才成为一条可证伪的断言。

修好这两点后，变异才精确打红 `F1 ★ 点「重试切换」真的切换了程序位`。
**这条经验比测试本身更值钱：先问「它怎么才能红」，再问「它是不是绿的」。**

三条最值得说的断言，因为它们各自守住本方案的一条核心主张：

- **`cap`** 守住「能力开关驱动 UI」—— 页面里一旦出现 `if (platform === "trae")` 式硬编码，它必红。
- **`ime`** 守住「搜索只重绘列表区」—— 整页重绘会打断中文输入法组词，它必红。
- **`progbind`** 守住「一个程序位同时只有一个账号、一个账号可绑 0..N 个程序位」——
  它回退的是**单绑定模型**（切一个程序位会顺手清掉本账号的其他程序位，
  等于「把 IDE 切到 X」会让 X 从 WorkBuddy 登出）。真实应用明确支持多绑定
  （`account-card.tsx` 的「使用中 N 个工具」徽章），所以这是**能力被砍掉**而不只是显示错误。

### 原型**不**覆盖的

真实 Tauri IPC、真实网络与 CORS、真实客户端的启动与凭据写入、性能与虚拟滚动。
这些必须在真实实现阶段按既有验证纪律单独证明（见 `webui-cdp-verify` 技能的 CDP 路径）。

另外：jsdom **不做布局**，所以换行、溢出、对比度这类问题它抓不到 —— 这些靠
系统 Chrome 的 `--headless=new --screenshot` 逐屏人眼看过。实测抓出过三条 jsdom
看不见的问题：已排除账号仍可「指定」、资源包重名、会话名与目录名逐字相同。

## 附录 C：原型 → shadcn 收敛清单（v2.1 新增，P3 前置）

项目规范要求「优先复用 shadcn/Radix 组件，缺组件补到 `src/components/ui/`，自研必须记录理由」。
原型是**原生实现**，落地时必须按下表收敛。**这不是「美化」，而是行为正确性**——
下面每一项的「缺了会怎样」都是真问题：

| 原型里的原生实现 | 应替换为 | 缺了会怎样 |
|:---|:---|:---|
| `#drawer`（手写 + `aria-hidden`） | Radix `Dialog` → `Sheet` | **焦点会逃到背景**；`aria-modal` 缺失；Esc / 焦点归还要手写 |
| `#palette`（手写列表） | `cmdk`（`Command`） | 方向键漫游、`aria-activedescendant`、结果播报全缺 |
| `<button class="check">`（勾选 / 三层会话树） | Radix `Checkbox` | 丢 `role="checkbox"` 与 **`aria-checked="mixed"` 半选语义** |
| 裸 `<table>` | `Table` | 丢 `aria-sort`（排序状态对读屏不可见） |
| `ViewParamBar` 的分段按钮 | `ToggleGroup` / `Popover` | 键盘漫游与选中语义缺失 |
| 抽屉内长列表 | `ScrollArea` | 滚动条样式与键盘滚动行为不一致 |
| 删除确认 | `AlertDialog` | 与 `Dialog` 语义混淆；破坏性操作需要强制焦点 |
| 作用域菜单 | `DropdownMenu` | 菜单语义 / 焦点归还 |

**本地 `src/components/ui/` 现有 16 个**（v2.3 逐个数过）：
`alert` `badge` `button` `card` `chart` `dialog` `dropdown-menu` `input` `label`
`select` `separator` `skeleton` `sonner` `switch` `tabs` `tooltip`。

**本方案需要、但目前缺失的组件**（按设计需求列，不按"通用组件库应该有什么"列）：

| 需要的组件 | 用在哪 | 缺了会怎样 |
|:---|:---|:---|
| **`sheet`**（Radix Dialog 侧向变体） | §3.5 账号详情抽屉、§3.15.2 会话关联图抽屉 | 抽屉没有标准实现，只能手写 ⇒ 焦点陷阱 / `aria-modal` / Esc / 焦点归还全要自己保证 |
| **`checkbox`**（含 `aria-checked="mixed"`） | §3.4 批量勾选、§3.14 备份三态、§3.15 会话树 | 丢半选语义，用户看不出"选了一部分" |
| **`table`** | §3.4 表格视图、§3.14 导入预览 | 丢 `aria-sort`，排序状态对读屏不可见 |
| **`popover`** | §3.9 `ViewParamBar` 的下拉参数 | 浮层定位与外部点击关闭要手写 |
| **`alert-dialog`** | 删除账号、§3.15.3 重启确认 | 与普通 `dialog` 混用，破坏性操作失去"强制焦点" |
| **`command`**（`cmdk`） | §3.7 命令面板 | combobox 语义 + 方向键漫游 + `aria-activedescendant` 全缺 |
| **`toggle-group`** | §3.9 `ViewParamBar` 分段按钮 | 键盘漫游与选中语义缺失 |
| **`scroll-area`** | 抽屉内长列表 | 滚动条样式与键盘滚动行为不一致 |
| **`accordion`** / **`collapsible`** | §3.9 设置页分组 | 展开/收起语义要手写 |
| **`radio-group`** | §3.15.2 分叉时「保留哪一份」 | 单选语义缺失 |
| **`hover-card`** | 账号卡悬停预览 | 延迟显示与焦点处理要手写 |
| **`time-picker`** | §3.9 签到执行时刻 | 时间输入的本地化行为不一致 |
