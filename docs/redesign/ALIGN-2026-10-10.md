### A. 图表 / 用量（3 项）

#### A1 ★ 堆叠柱「列数 = 天数」不成立，且日均分母错 —— 严重度：高 ✅ **已修**

| 项    | 内容                                                                                                                                     |
| :--- | :------------------------------------------------------------------------------------------------------------------------------------- |
| 原型要求 | 堆叠柱列数 === 天数窗口（`verify-behaviors.cjs:722` 断言 `cols.length === 30`）；`range=7` 时首列落在 7 天窗口内                                              |
| 当前实现 | `src/lib/usage-charts.ts:248` `lastDays()` 用 `.slice(-range)` 切**稀疏数组**；`src/pages/TokenStatsPage.tsx:134,143`                         |
| 实测推演 | `daily` 只有 5 天数据 + `range=30` ⇒ **只出 5 列**；`range=7` 时首列落在 **08/12**（超窗口 59 天）                                                         |
| 根因   | 后端 `crates/buddy-switch-core/src/modules/token_stats.rs:340` `daily: HashMap<String, Totals>`，`.or_default()` 只在**有记录的日子**落条目 ⇒ 缺失日不存在 |

**同根因引发 3 个可见错误**（必须一并修，否则修一半仍自相矛盾）：

1. 列数 ≠ 天数 —— 原型断言直接判红；
2. `range=7` 却显示 59 天前的数据，而标签写「近 7 天」（`wbStats.zh.ts:172`）⇒ **图文不符**；
3. `TokenStatsPage.tsx:151` `average = total / columns.length`，分母是「**有数据的天数**」而非窗口天数  
   ⇒ 实测 1500 Token / 5 天显示「日均 300」，真实 30 天日均应为 50，而 `wbStats.zh.ts:185` 的 hint 恰恰写着  
   「**按自然日平均**」⇒ **文案与算法互相矛盾**。

**改法**：`lastDays()` 改为按 `Date.now()` 倒推 N 个**日历日**窗口，缺失日补 0（与既有 `heatmap` 补 0、  
`expiry` 补 0 同一手法，`:409-424` 有先例）。后端**不动** —— 前端补齐即可，避免动 `HashMap` 契约。

### C. 备份 / 导入（1 项，安全相关）

#### C1 「重试失败项」按钮实为「重新选文件」—— 中 ✅ **已修（走了「真重试」路线）**

| 项 | 内容 |
| :--- | :--- |
| 原型要求 | 部分失败态的出口是「**只重试失败项**」 |
| 原实现 | `backup-section.tsx:568` 文案取 `backup.import.result.retry` = 「重试失败项」/ "Retry failed items"，但 `onClick={chooseFile}` ⇒ **打开文件选择器、整份重来** |
| 危害 | **安全相关**：用户以为只重试失败项（增量），实为整份重新导入（覆盖语义）。文案与行为相反，是本轮最典型的「假控件」 |

**本批改法**（复核后发现**不必新增命令**）：

1. **失败单元本来就是 scope** —— `backup.rs::import_backup` 是**逐 scope 事务**，`perScope` 每行粒度即 scope
   ⇒「只重试失败项」的最细诚实粒度**恰好就是 scope**。因此**改现有命令加可选 `onlyScopes`** 即可，
   不必新增 `import_backup_items`（省掉四通道新增风险）。
2. **core**：`import_backup(text, policy, selection, only_scopes)`；名单非空时
   **名单外的 scope 连读都不读**（不是「读了再跳过」）⇒ 名单外的坏分区不会让重试整体失败。
3. ★ **顺带修掉一个更隐蔽的假出口**：此前**未知 scope 也被计入 `retryable`**，而键名非法是
   来件的结构性缺陷、重试必然再失败 ⇒ 现改为 `retryable: false`，并新增 `retryableScopes`
   让前端能拿到**要回传的具体 id**。
4. **前端**：`retryFailed()` 复用同一份 `fileTextRef` + 只传 `retryableScopes`，**不再要求重选文件**。
5. **诚实文案**：`failed` 计的是 **scope 数**，原文案「{count} 个账号导入失败」是**错的** ⇒ 改为「{count} 个分区导入失败」。

⚠️ **重试不是事务回滚**：一个 scope 内 3 个 section 共用一个 `Result`，若第 2 个写失败、第 1 个**已落盘**；
重试时已落盘的 section 在 `KeepLocal` 下计「跳过」⇒ 结果收敛且不丢数据（已写入函数文档与测试）。

### ⚠️ 两个「门禁自己写错」的真实教训

写门禁时我踩了 7 次正则太窄/太宽（注释未剥导致把**禁令说明**当成违规、
`/>` 收尾、带逗号条目、变量改名后字面量对不上）。**每次都是门禁红而代码对**。
⇒ 纪律：**门禁写完必须先跑一遍**；红了先问「是不是我的判据写错了」，
再问「是不是代码真的错了」。这个顺序能省掉大量误改。

同样地，`apikey::masked_is_an_explicit_non_secret_whitelist`（**既有**安全测试）
在 E3 加 `suffix` 时变红 —— 那是它**该**做的事（掩码视图的键必须**显式批准**），
于是把 `suffix` 写进白名单并补「恰好 4 位」的断言，而不是绕过它。
