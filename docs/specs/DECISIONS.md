## A. 架构与状态真值（D1–D4、D12）

### D1 统计页的「合并（all）」放在哪

**问题**：现在「合并全部作用域」是统计页内的二态开关。要不要提升为第 5 个作用域「全部」？

- **推荐：保留为页内二态开关。**
- **理由**：**作用域决定「数据从哪来」，开关决定「怎么看」**。合并是视图行为，不是数据域。
- **定了会动什么**：作用域选择器保持 **4 项**；`Scope` 枚举不加伪成员。
- **选反方案的代价**：提升为「全部」后，「当前登录账号」「签到」「切换」等**账号类操作在「全部」下失去语义**——
  它们必须绑定到一个具体 scope，UI 上要么禁用要么要求再选一次，等于把问题推给用户。

### D2 页面合并的激进程度

**问题**：五个工作台（概览/账号/用量/会话/网关/设置）是一次合完，还是分批？

- **推荐：用量 → 网关 → 设置 → 账号**（⚠️ 与 v2 初稿的顺序**相反**）。
- **理由**：代码事实是**设置页差异最大**（WB 7 卡 vs Trae 10 组，仅网关/签到重叠），
  用量页同构度最高（两平台都是 4 组视图参数）。先合同构度高的，能最快验证「能力开关驱动」这套机制是否成立。
- **定了会动什么**：P3 拆成 4 个可独立验收的小步。
- **选反方案的代价**：先合设置页会在最复杂的地方验证机制——一旦机制不成立，返工面积最大。

### D3 应用级设置入口

- **推荐：留在侧栏底部。**
- **理由**：改动最小、位置稳定；用户已经形成肌肉记忆。
- **定了会动什么**：顶栏不放设置入口（顶栏已有作用域、搜索、刷新、主题四个元素）。
- **选反方案的代价**：迁到顶栏溢出菜单更符合规范，但**用户要重新学习位置**，且顶栏更挤。

### D4 是否接受路由改为 `/s/{scope}/{dest}`

- **推荐：接受。**
- **理由**：换来「**状态单一真值**」——刷新、前进后退、分享链接行为一致，
  彻底消灭「账号页用组件 state、统计页用 localStorage」的分裂。
- **定了会动什么**：`/` 与 `/trae/*` 全部重定向到新路由；旧书签不失效。
- **选反方案的代价**：不统一的成本是持续的——每加一个页面都要重新决定"状态放哪"。

### D12 Trae 的 10 组设置如何装进子导航

**问题**：公共子导航是 9 项，Trae 有 10 组设置，硬压进去会导致某些子项名不副实。

- **推荐：允许「平台专属子项」** —— `PlatformDescriptor` 除 `destinations` 外，还能声明自己的设置子项。
- **理由**：硬压进公共 9 项，会出现「通用」里塞 Trae 专属项这种名不副实的归类。
  平台专属子项让**公共部分保持公共，差异部分显式声明**，与 §2.3 注册表的思路一致。
- **定了会动什么**：`PlatformDescriptor` 增加一个字段；设置页子导航 = 公共项 ∪ 平台项。
- **选反方案的代价**：全部压进公共项 ⇒ 设置页对 WorkBuddy 用户显示 Trae 专属项（或反过来），
  要么显示无关项、要么加平台判断（后者违反「不许 `if (platform)`」）。

## B. 迁移顺序与回滚（D2、D6、D13）

### D6 旧 UI 双跑期 vs 一次性切换

- **推荐：分阶段** —— P1/P2 **保留旧 UI 可回退**，P3 起才切换。
- **理由**：P1（状态容器）与 P2（骨架布局）是风险最高的两步，保留旧 UI 等于随时能止损。
- **定了会动什么**：P1/P2 期间新旧页面共存，需要一个开关决定走哪套。
- **选反方案的代价**：一次性切换 ⇒ 出问题时没有退路，只能回滚代码。

### D13 每期回滚策略是否按 §5 执行

- **推荐：按 §5 执行**，特别是 **P3 保留 `src/pages/legacy/`**。
- **理由**：路由能切回是**唯一能快速止损**的手段；删掉旧页面只需一行 `rm`，但恢复要重写。
- **定了会动什么**：`src/pages/legacy/` 目录在 P3–P5 期间存在。
- **选反方案的代价**：不保留 ⇒ 每个 UI 缺陷都变成"必须立刻修好"，没有缓冲。

## C. 目的地与 IA（D5、D11、D19）

### D5 Trae 程序位在各作用域下的默认策略

**问题**：国内版 / 国际版是否应有各自不同的默认程序位？（v1 提过，v2 初稿丢失，一直没答案）

- **推荐：按 scope 记住上次选择**，首次使用取「该 scope 下已检测到的第一个」。
- **理由**：这是**零配置的正确做法**——用户在某 scope 下的常用程序位本来就不同，
  记住上次比任何硬编码默认值都准。硬编码默认值的问题在于：它假设了所有用户的使用习惯一样。
- **定了会动什么**：新增一个按 scope 键控的偏好存储；P4「程序位常显」时直接可用。
- **选反方案的代价**：硬编码默认 ⇒ 每次切 scope 都要手动改一次，高频摩擦。

### D11 是否认可新增「概览」目的地

- **推荐：认可。**
- **理由**：解决「打开应用不知道先看什么」；且它**不承载写操作**，风险低。
- **定了会动什么**：目的地集合含「概览」，它同时是默认落地页。
- **选反方案的代价**：没有概览 ⇒ 用户每次都要自己找「哪里有问题」（过期账号、未签到、待同步会话）。

### D19 侧栏默认 6 项是否认可

- **推荐：认可**（新增「会话」为第 6 个目的地）。
- **理由**：会话管理是「账号之间关系」的属性，**账号页装不下**——
  硬塞进去会让账号页承担两套心智模型。
- **定了会动什么**：侧栏 6 项 + 每项可被用户隐藏（§3.2）。
- **选反方案的代价**：并入「账号」当子 Tab ⇒ 账号页同时回答"我的账号怎么样"和"我的会话同步了吗"两个无关问题。

## D. 工程规范与范围（D7–D10）

### D7 原型与 shadcn 的收敛基准

- **推荐：以 Rhea 令牌 + shadcn 为准，原型仅作交互参考。**
- **理由**：项目规范要求优先复用 shadcn/Radix；原型是原生实现，且自建了 `--s1..--s8` + `success`/`warning`，
  与 `index.css` **不同源**（后者只有 `chart-1..5`）。
- **定了会动什么**：附录 C 的 **12 类组件**要补齐；`index.css` 要先补 8 色序列 + 语义色。
- **选反方案的代价**：照原型实现 ⇒ 要么重造轮子（手写焦点陷阱、半选语义），要么视觉与真实应用漂移。

### D8 i18n 规模与负责人

- **推荐：实现者随代码同步补，不单独排期。**
- **理由**：`locales/zh.ts` 是**编译期键类型** —— 漏词条 `tsc` 直接红，**编译器会强制**，不需要额外流程。
- **规模估算**：新增术语约 30–40 键 + 设置子导航 9 项 + 会话/网关新文案 ≈ **60–80 键 × 2 语言**。
- **定了会动什么**：无额外排期；但每个 PR 都要带词条。
- **选反方案的代价**：单独排期做 i18n ⇒ 要么阻塞功能开发，要么功能先上、词条后补（期间 `tsc` 红）。

### D9 账号列表虚拟滚动是否进 P4

- **推荐：不进 P4，先量化再决定。**
- **理由**：符合项目纪律「**先量化再投入**」。先测「账号数达到多少时全量渲染会卡」——
  若典型用户只有 10–30 个账号，做了就是过度工程。
- **定了会动什么**：P4 不含虚拟滚动；若实测需要，作为独立小项后补。
- **选反方案的代价**：先做虚拟滚动 ⇒ 与「卡片/表格切换、分组」等交互耦合，复杂度显著上升。

### D10 webui / demo 模式是否同步改造

- **推荐：同步改造。**
- **理由**：三种形态共用同一套 `api.ts`；不同步会导致 webui 版与新 UI 不一致。
  demo 模式（`screenshot-demo.ts`）则只需在**新增只读命令时补 case**（门禁已强制）。
- **定了会动什么**：改造范围 ×3 形态；`check-api-contract.cjs` 第 6 条继续兜底。
- **选反方案的代价**：只改桌面版 ⇒ webui 用户看到旧 UI，且两套代码分叉后难合并。

## E. 全局备份与恢复（D14–D18）

### D14 默认勾选范围

- **推荐：默认全选全部作用域。**
- **理由**：备份的主要场景是**换机/灾备**，那时用户要的就是"全部"。
- **定了会动什么**：导出面板初始态全选。
- **选反方案的代价**：默认只勾当前 ⇒ 换机要手动补 3 次，且**很容易漏**（漏了还以为备份完整）。

### D15 凭据开关默认值

- **推荐：默认关。**
- **理由**：**安全默认**。文件里不含凭据时，即使泄露也只是账号清单，不含可直接使用的登录态。
- **定了会动什么**：导出面板初始态不含凭据；打开时出现红色警告 + 二次确认。
- **选反方案的代价**：默认开 ⇒ 用户可能在不知情的情况下导出明文 token 并随手分享。

### D16 导入冲突默认策略

- **推荐：保留本地。**
- **理由**：最不易误伤。导入是"补数据"，不该默认覆盖用户已有的东西。
- **定了会动什么**：导入预览的默认冲突策略。
- **选反方案的代价**：默认覆盖 ⇒ 用户想"补几个账号"结果把现有配置冲掉了。

### D17 是否做定时自动备份

- **推荐：做** —— 每日一次，保留最近 7 份，存 `backup_dir()`。
- **理由**：备份功能的价值在于**出事时有**，而用户不会记得手动备份。
  体积可忽略（单份几十 KB，7 份几百 KB）。
- **定了会动什么**：`BackgroundTask` 表加一条（**两侧宿主都要加**，见项目硬约束）；设置页给开关。
- **选反方案的代价**：只做手动 ⇒ 真正需要时没有备份（这正是备份功能最常见的失效方式）。

### D18 导入前自动快照是否强制

- **推荐：强制，不可关闭。**
- **理由**：它是「导入可撤销」的**后端支撑**。可关就等于把兜底撤了，
  而 UI 上又承诺了「可从自动备份恢复」——**承诺与能力必须一致**。
- **定了会动什么**：设置页不出现这个开关。
- **选反方案的代价**：可关 ⇒ 用户关掉后导入出错，既没有撤销也没有快照。

## F. 会话工作台与展示（D20–D22）

### D20 会话工作台的范围

- **推荐：先做「查看 + 安全同步」**，分歧处理后置。
- **理由**：分歧处理是复杂交互（要逐条 diff、要选保留哪一份），且需要后端支持内容级比较。
  「查看 + 安全同步」（加法同步落后副本）已能覆盖大部分场景。
- **定了会动什么**：P8 范围缩小；分歧组**只展示不提供统一入口**（明确提示"需要逐条处理"）。
- **选反方案的代价**：一次做全 ⇒ P8 周期显著拉长，且最复杂的部分拖累最常用的部分。

### D21 桌面悬浮窗是否进本期 —— ✅ **进本期**（唯一与推荐不同的决策）

**拍板结论（2026-10-03）：进本期。**

- **原推荐**：不进本期，只保留 IA 占位。
- **拍板改为**：**进本期**，作为 **P9** 正式排期。
- **原推荐理由**（保留备查）：它是独立能力，与「作用域 / 工作台 / 注册表」这套重构互不依赖；
  单独立项可以有它自己的窗口管理与独立的键盘可达性验证。
- **定了会动什么**：
  - **P9 从「暂不排期」变为正式期次**（建议与 P8 并行或紧随其后）；
  - `PLAN.md` §3.16 的措辞从「IA 占位」改为「**本期交付**」；
  - **需要一条独立的验证路径**：悬浮窗是独立窗口，**不能复用主窗口的键盘可达性验证**；
  - 它是独立窗口 ⇒ 需要**宿主侧入口**（托盘 / 侧栏左下角）；
    按项目硬约束，新增「写状态 / 周期性」出口要 **grep 两侧 `BackgroundTask` 注册表**确认是否需登记状态轮询。
- **风险与对策**：并进本期会把「独立窗口的复杂度」混进重构，出问题时**难以归因**。
  ⇒ 对策：**P9 与 P0–P8 解耦**（除注册表外不共享代码），且**排在 P8 之后启动**，
  避免两条复杂线同时进行。这也是原推荐"不进本期"的核心理由——现在改成用**解耦 + 顺序**来化解，而不是靠推迟。

### D22 账号显示字段默认值 + 邮箱脱敏

- **推荐：默认「备注」；邮箱默认脱敏。**
- **理由**：备注是**用户自己写的**，通常最有辨识度（"主号""团队共用"）。
  邮箱脱敏防的是**截图泄露**——本项目的用户经常贴截图报障，这是真实高频场景。
- **定了会动什么**：`displayName()` 的默认分支；`accountIdentity()` 的脱敏默认开。
- **选反方案的代价**：默认账号名 ⇒ 多个账号名相似时（`jackey` / `jackey2`）难以区分；
  不脱敏 ⇒ 求助截图里泄露完整邮箱。

## G. 网关、模型与接入（D23–D28）

### D23 自动探测的触发范围

- **推荐：绑定凭据成功后立即探测 + 网关启动时仅当清单为「内置」**（手动刷新保留）。
- **理由**：绑定后探测是「接入即识别」的落点，必做；
  启动时补一条**仅针对「从未成功过」**的场景，让首次失败能自愈。
  不做「每次切作用域都探测」——那会在用户切换时打上游，收益不抵请求成本。
- **定了会动什么**：探测时机表（§3.17.2）。
- **选反方案的代价**：全时机自动探测 ⇒ 上游请求量上升，且用户感知不到收益。

### D24 是否做「识别后轻量校验」

- **推荐：不做。**
- **理由**：为每个模型发一次请求，**慢且耗额度**。而不做校验时，文案写「**已识别** N 个模型」是诚实的
  （不承诺"可用"）。用户首次调用遇到问题，错误信息本身就能说明。
- **定了会动什么**：文案口径固定为「已识别」，不出现「N 个模型可用」。
- **选反方案的代价**：做校验 ⇒ 接入后要等 N 次请求；且校验通过也不代表后续不会因额度/限流失败。

### D25 模型清单是否允许手动覆盖

- **推荐：允许「添加」，不允许「删除上游条目」。**
- **理由**：上游清单不准时用户能补上（应对上游滞后）；
  但删除上游条目会与「清单 = 事实」冲突——**要"隐藏"就用禁用**（D26），禁用是软删除，语义更清楚。
- **定了会动什么**：清单有「来源」标记（上游 / 手动）；下次探测时**手动条目保留**。
- **选反方案的代价**：允许删除 ⇒ 下次探测又回来了（用户会以为设置没生效）；
  完全只读 ⇒ 上游漏报时用户无解。

### D26 被禁用的模型是否仍可见

- **推荐：可见但标灰。**
- **理由**：用户需要知道**它存在、且可随时启用**。彻底隐藏会导致"我明明记得有这个模型，怎么找不到了"。
- **定了会动什么**：模型页的 `row-off` 样式 + 「启用」按钮常驻。
- **选反方案的代价**：彻底隐藏 ⇒ 用户无法发现自己曾经禁用过它，也就无法恢复。

### D27 禁用模型的默认范围

- **推荐：默认全开。**
- **理由**：**不替用户做决定**。预置禁用高消耗模型看起来贴心，但用户不知道被禁了，
  调用失败时会怀疑网关有问题。
- **定了会动什么**：新 scope 的 `disabled` 初始为空。
- **选反方案的代价**：预置禁用 ⇒ 静默的能力缺失，比报错更难排查。

### D28 接入说明的工具清单如何维护

- **推荐：硬编码在词条里。**
- **理由**：客户端接入方式变化不频繁；做成可配置数据会引入新问题
  （配置从哪来？远程更新要不要签名？离线怎么办？），而收益只是"加客户端不用发版"。
- **定了会动什么**：`ACCESS_TOOLS` 常量 + 词条。
- **选反方案的代价**：做成可配置 ⇒ 多一套数据来源与更新机制，且**未确认的客户端仍不能编造**（§3.18.3）。

## H. 请求代理与无缝切号（D29–D32，v2.7 新增，**待拍板**）

> 背景：让网关代理客户端的业务请求，由网关按请求选号 ⇒ **动态无缝切号**（不写文件、不重启客户端）。
> 完整设计见 `PLAN.md` §3.19。**⚠️ 该功能有硬门槛（证书固定），P12a spike 不通过就整个作废。**

### D29 拦截方式选哪条 —— ✅ **已拍板（2026-10-03）：只用 A / C，排除 B，且默认关**

**拍板结论**：

- **排除 B（hosts + 本地 TLS）** —— 用户明确要求「**不劫持客户端的请求**」；
- **只保留 A（客户端配代理）与 C（客户端配 base URL）** —— 都是**客户端主动委托**；
- **代理开关默认关**。

⚠️ **必须接受的代价**：排除 B 之后**没有兜底** ⇒ **A / C 都不可行时 P12 直接作废**。
这是**有意接受的取舍**：**宁可功能做不成，也不动用户的系统解析**。

**原推荐（「先 A 后 B」两步走）作废**，保留备查：它把 B 当"最后手段"，
理由是 A / C 依赖客户端配合而 B 不依赖 ——
但 **「不劫持」的优先级高于「功能做得成」**。

**验证顺序**（§3.19.11）：步骤 0 先查 C（最便宜）→ 步骤 1 只配代理不装 CA → 步骤 2 装 CA + 中间人。
**任一步失败即出局；全部出局 ⇒ P12 作废。**

### D30 代理默认范围

- **推荐：只代理业务 API 域**（§3.19.2 ① 表）。
- **理由**：最小必要。网页域 / CDN 走代理**收益低、暴露面大**。
- **定了会动什么**：白名单内容。
- **选反方案的代价**：全代理 ⇒ 网关能看到用户在客户端里的**一切网络行为**，远超功能所需。

### D31 粘性窗口多长

- **推荐：约 5 分钟（一次业务操作会话）**。
- **理由**：太短 ⇒ 用户看到积分 / 状态在账号间跳动；太长 ⇒ 失去「动态」的意义。
- **定了会动什么**：`StickyTable` 的过期策略。
- **选反方案的代价**：不粘性 ⇒ 界面数字乱跳；粘太久 ⇒ 等于没做动态切号。

### D32 CA 安装方式

- **推荐：引导用户手动安装。**
- **理由**：用户知情、责任清晰；代装需要更高权限，且很难说清「装了什么」。
- **定了会动什么**：开启流程的步骤数（手动装多一步）。
- **选反方案的代价**：代装 ⇒ 省事，但用户不知道系统里多了个根证书 —— **卸载不干净会留下长期隐患**。

### D33 A 路的「中间人解密」是否可接受 —— ✅ **已确认（2026-10-03）：宽口径**

**结论：宽口径** —— 「不劫持」= 不改 hosts / 不做 DNS / 不做透明代理；
**用户显式信任 CA 的中间人不算劫持**。⇒ A 路可用，**P12 保留**。

**判据（为什么宽口径是对的）**：区分「劫持」与「中间人」的标准**不是"是否解密"，而是三条**：

| | B（hosts 劫持） | A（客户端配代理 + 显式装 CA） |
|:---|:---|:---|
| **知情** | ❌ 用户不知道系统解析被改了 | ✅ 显式开启开关 + 显式安装 CA + 列出代理域名 |
| **影响范围** | ❌ **全机**所有程序 | ✅ 只有**配置了代理的那个客户端** |
| **可撤** | ⚠️ 容易忘还原，残留是隐患 | ✅ 撤代理 + 移除 CA，**一键还原** |

⇒ **B 三条全不满足，A 三条全满足** ⇒ 宽口径不是"放宽"，而是**按正确的判据分类**。

**但宽口径附带三条硬边界**（缺一不可，已写进 §3.19.4 / §3.19.7）：
① 只代理**白名单域**；② **不落盘正文**（日志只记元数据）；③ **默认关 + 一键还原**。

⚠️ **诚实说明残留风险**：开启期间，**网关确实能看到客户端的全部业务流量**（含账号身份）。
这不是可以"消除"的，只能靠上面三条边界**限制范围与留存**。
**用户开启时必须在界面上看到这句话**，而不是藏在文档里。

### D34 P12 的内部顺序：**C 先行**（✅ 已确认 2026-10-03）

**结论**：P12 **不要一上来做 A（中间人）**，**先做 C（改 base URL）**。

**理由（这是本轮最要紧的一个判断）**：

| | **C**（改 base URL） | **A**（代理 + 中间人） |
|:---|:---|:---|
| 需要 CA / TLS | ❌ **不需要** | ✅ 需要 |
| 实现成本 | **低** —— 本仓本来就在写客户端配置，路径相同 | 高 —— 转发层 + 解密 + 证书固定风险 + 一键还原 |
| 覆盖范围 | **LLM 调用**（**高频**） | **业务请求**（签到 / 积分，**低频**） |
| 风险 | 低 | 高（能看到全部流量） |

⚠️ **一个决定性的事实**：本仓的**签到 / 积分是它自己直接调上游**的（`checkin.rs` / `credits.rs`），
**不经过客户端** ⇒ 客户端侧的业务请求 = 「用户在客户端里点开看积分」这类**低频操作**。

⇒ **A 的收益集中在低频场景，成本却最高** ⇒ **先做 C；A 等 C 落地后再评估值不值得**。

**定了会动什么**：§3.19.9 的 P12 三步顺序调整为 ——
**P12a spike（步骤 0 先查 C）→ P12b = C 路 → P12c = A 路**。
**若 spike 步骤 0 判定 C 不可用**，则回到 A，**并且要重新评估是否值得做**（因为此时只剩低频收益）。

## I. 对齐轮的待确认项（Q1–Q7，v2.8，**2026-10-10 已拍板**）

> 背景：`ALIGN-2026-10-10.md` §4 列了 7 项「不臆测、需拍板」。本节把它们**逐条落成决策**，
> 口径仍是本文件的一贯纪律：**拍板要写清「推荐 / 理由 / 定了会动什么 / 反方案代价」**。

### D35 Q1 · WorkBuddy 侧的「危险操作」放什么 —— ✅ **已拍板（2026-10-10）**

**结论**：WB 侧新增「危险操作」分区，只放**两项**：
**导出诊断包**（新建命令）+ **清空网关请求日志**（复用既有 `clear_gateway_logs`）。
**刻意不做「重置设备标识」。**

**理由（「重置设备标识」为什么不能照搬）**：

| | Trae 的重置 | WB 的实情 |
|:---|:---|:---|
| 改什么 | Trae 客户端自己的 6 层文件（`machineid` / `aha/TinyStorage` / `trae-webview` / 注册表 `MachineGuid` …） | **这些结构 WorkBuddy 客户端根本没有** |
| 本工具自身的身份 | 客户端侧标识 | `sha256("wb2a:<purpose>:<uid>")` **纯函数派生**（`gateway/session_headers.rs`）——**不落盘、无状态** |

⇒ 给 WB 加这个按钮，只能「重置空气」—— 那是本仓最忌的**假控件**
（与 §3.5「承诺了做不到的事」同罪）。**产品决策，不是漏做。**

**顺带纠正原文档的一处不准确**：ALIGN §4 Q1 写「真实：**Trae 侧有**（重置设备标识 + 导出诊断包）」——
**「导出诊断包」在真实代码里此前根本不存在**（前端 0 命中、后端 0 命中，只有原型有），
不是「Trae 有、WB 没有」。本决策据此按「新建 WB 能力」处理。

**诊断包的安全红线**（与备份**共用同一套**判据，杜绝漂移）：
实现层按 `backup::CREDENTIAL_KEYS` 递归剥离；验收层把产出当**纯文本**搜同一组键
⇒ **0 命中**，命中即**拒绝返回**（fail-closed）。刻意**不含会话正文**
（含用户真实项目路径，`MEMORY-10` 红线，对定位本工具自身问题也无帮助）。

- **定了会动什么**：新建 `core/modules/diagnostics.rs` + `export_diagnostic` 四通道
  （`api.rs` 路由+handler / `commands.rs` / `lib.rs` / `api.ts` ROUTES+wrapper）；
  `SettingsPage` 的 `diagnostics` 分区加卡；`wbSettings.danger.*` 词条。
- **选反方案的代价**：把「重置设备标识」硬加上 ⇒ WB 用户点到一个**没有效果**的按钮
  （比没有这个按钮更糟：它会让用户以为设备标识被清了）。

### D36 Q2 · 「指定」按钮对不可用账号是否禁用 —— ✅ **已拍板（2026-10-10）：不禁用**

**结论**：维持现状 —— **不**因账号冷却 / 禁用 / 零积分而禁用「指定」按钮。

**理由**：指定是**偏好而非约束**。后端 `pick_with_preference`（`gateway/pool/pick.rs`）
在指定账号不可用时**回落到自动择优**，**不会拒绝服务**。若前端把它禁掉，用户就**无法预先指定**
一个「正在冷却、等下就恢复」的账号 —— 那恰恰是偏好最有用的场景。

⚠️ **原型 F6 的「已排除」在本仓不是数据模型**：真实状态是五态枚举
（`available` / `cooling` / `disabled` / `expired` / `no_credits`，`types.ts::GatewayPoolAccount`），
`excluded` 字段**全仓零命中**。⇒ 原型那条断言**无对应实体**，属**原型反例**。

- **定了会动什么**：仅补门禁（把「不按状态禁用 pin」钉住，防后人好心改成禁用）+ 把
  「偏好而非强制」的说明留在行内（`shared.gateway.pool.preferredHint` 已有）。
- **选反方案的代价**：禁用 ⇒ 用户不能预设恢复中的账号；且与后端「会回落」的行为**自相矛盾**
  （按钮灰了，但已指定的账号仍会在可用时被选中）。

### D37 Q3 · 概览「今日 Token」与账号卡口径 —— ✅ **已拍板（2026-10-10）：改名区分，不合并口径**

**结论**：**不**给概览补网关聚合；改为把概览那一格改名为「**客户端 Token（今日）**」，
并在 tooltip 写明「仅客户端自身用量，不含经本网关的请求」。

**理由（三条实测事实）**：

1. **两个来源是互斥的，不是重复**：`MEMORY-10` §一 —— 网关只覆盖走 Base URL 的外部 API 调用，
   **客户端直连上游，不流经网关**。⇒ 两个数字**各自都对**，只是含义不同。
2. **合并会让概览自相矛盾**：概览的趋势卡是 14 天**客户端**轴；若只把今日这一格加上网关，
   就会出现「今日格 ≠ 趋势最后一根柱子」。**同一页内部对不上**，比口径不同更糟。
3. **补网关聚合拿不到历史**：`token_daily` 只投影**今日**（`account_token_today`），
   没有 14 天轴 ⇒ 要补就得新建一套历史聚合，属另一个量级的改动。

**同名才是真 bug**：两个格子都叫「今日 Token」，用户会默认它们该相等，
然后得出「数据错了」的结论。**改名即可消除这个误解，成本最低、不引入口径漂移。**

- **定了会动什么**：`wbOverview.stat.tokens` 改名 + 新增 `tokensHintClientOnly`；
  `StatTile` 增 `title` 字段（口径说明走 tooltip，不挤占随数据变的 `hint`）。
- **选反方案的代价**：硬合并 ⇒ 要么趋势与今日对不上（口径2），要么新建历史聚合链（口径3）。

### D38 Q4 · 头像底色对比度 —— ✅ **已拍板（2026-10-10）：按实测修，不按估算判罪**

**结论**：实测 `bg-success/15 + text-success`（亮色）为 **3.11:1**、
`bg-warning/15 + text-warning` 为 **3.17:1**，**均低于 AA 的 4.5:1** ⇒ **判为真缺陷并修**。

**为什么必须实测**：原型断言读的是 `oklch()` 字面量，真实实现用 Tailwind 语义 token
⇒ 断言体**不可直接迁移**。本条的做法是**把 oklch 换算到 sRGB 再算 WCAG 比值**，
而不是照抄断言里的 `L ≤ 0.5`（oklch 的 L 与 WCAG 亮度不是同一个量）。

- **定了会动什么**：两条语义色头像 tone 改为固定色板（同其余 4 条的做法），并补门禁钉住比值。
- **选反方案的代价**：不动 ⇒ 头像首字在亮色主题下**读不清**（≈ AA 线的 70%）。

### D39 Q5 · 全部模型被禁用时计数行消失 —— ✅ **已拍板（2026-10-10）：始终渲染**

**结论**：计数行改为**只要有模型清单就渲染**（`total > 0`），`served = 0` 时也显示「当前暴露 0 / N 个」。

**理由**：`served === 0` **不是「无数据」**，而是「全部被禁用」这一**真实且需要被看见**的状态 ——
恰恰是用户最需要确认「禁用真的生效了」的时刻。此前的 `served > 0 &&` 守卫把这条信息
在最该出现的场景下藏了起来（这与「两个出口」说明**恒渲染**的处理自相矛盾）。

- **定了会动什么**：`model-list.tsx:172` 的守卫条件；文案沿用 `shared.gateway.models.count`
  （**不新增措辞**，避免踩「禁止 N 个模型可用」的反向断言）。
- **选反方案的代价**：保持原样 ⇒ 全禁用时页面**看不出**是否真的全禁了。

### D40 Q6 · 「登录态快照」是否升为 `Capability` —— ✅ **已拍板（2026-10-10）：不升**

**结论**：维持「按页面归属」，**不**把 `snapshot` 加进 `Capability` union。

**理由**：`Capability` 的语义是「**跨目的地复用的功能门控**」（侧栏 / 路由 / 动作可见性），
而登录态快照是**设置页内的一个分组**，只归 `TraeSettingsPage` 所有、不跨页复用。
升格会牵动 `Capability` union（前端 `registry.ts` + 后端 `capability.rs` 的 `[Capability; 7]`

**结论**：卡片上的程序位控件比 `WORKBUDDY_PROGRAMS` / 后端 `PROGRAMS` **多一个 WorkBuddy 主位**，

1. **主位不是同类操作**。`PROGRAMS` 的 5 项是「切换某个**外部**程序位」；

- **三条硬约束**（不可放宽）：① **永不失败**（日志是旁路能力，IO 错误内部吞掉，
  出错时不得回调自身）；② **有界**（4 MiB × 4 分片/天 × 7 天 ⇒ ≤112 MiB）；
  ③ **出站脱敏**（`redact`：`name=value` 凭据名 + `Bearer` + JWT 三形态，写盘前过）。
- **与另两份日志的分工**（刻意不合并）：本模块 = 本工具自己做了什么；
  `gateway_logs.json` = 客户端经网关发了什么（JSON、面向统计）；客户端日志 = 上游客户端自己写。
- **本机路径**照写（与「诊断包」相反 —— 那份是**发给别人**的，路径一律不出现）；
  路径统一成正斜杠（Windows `display()` 的 `C:/a\b` 混用形式贴进 issue 易错）。
- **选反方案的代价**：只在启动时裁一次保留 ⇒ 连跑数周的长驻进程会让「7 天上限」失效；
  不脱敏 ⇒ 日志文件被贴进 issue 时带着 token 一起走；直接 `eprintln!` 转发 ⇒
  一次 panic 就把「日志模块」变成新的故障源。

### D52 `auto_failover` 的作用域 = **产品线级**，不做 per-account —— ✅ **已落地（2026-10-30，issue #129）**

**结论**：`auto_failover` 是三份网关配置（WB `GatewayConfig` / Trae / Qoder）各一个同名布尔，
**默认 `false`**；界面上是账号池卡片工具条里的一个开关，WB 的两个版本 Tab 共用同一个值。
开关开启后：流中途的账号级失败不再补终止标记，而是发一条**可重试**错误帧（429 / 502），
由客户端整步重跑；同时写冷却、解绑粘性、写 `last_error`、日志记真实状态码。

**理由**：这个开关改变的是**对外字节语义**（从「假成功」变「显式错误」），
它描述的是「这台网关遇到账号故障时希望客户端怎么反应」，而不是「某个账号的偏好」。

- **不选 per-account 的代价**（即选反会怎样）：池里每个号都要维护一个布尔 ⇒
  新增账号默认值是什么？导入时怎么迁移？「A 号开着 B 号关着」时，一次失败到底按谁的？
  三个问题都没有非任意的答案，而答案是任意的时候，用户永远不知道该信哪个；
- **不选全局单开关的原因**：三条产品线的配置本来就分文件（`gateway_config.json` /
  `trae/api_gateway.json` / `qoder/gateway_config.json`），合并成一个跨产品线的开关
  会造出一个「不在任何一份配置文件里」的状态 —— 备份 / 导入 / Docker 挂载全都对不上；
- **不放进 `PoolConfig`**：那份配置**启动期固化**（`Pool::new` 克隆一次、运行期无 setter），
  而本开关必须热生效 ⇒ 与 `max_rotate` 同层放 config 顶层，每轮读 `config_snapshot()`；
- **默认关**：它改变对外报错方式，属于可感知的行为变更，不能让升级悄悄改变既有表现；
  「不勾选 = 回归基线」也顺带成了天然的回归测试（关闭态 7 条不变量各有单测，
  见 [`ACCOUNT-FAILOVER.md`](ACCOUNT-FAILOVER.md) §5/§7）。

### D53 Anthropic 出口的 `input_tokens` = **估算占位 + 末帧校正**，不写 0 —— ✅ **已落地（2026-10-30，issue #139）**

**结论**：`/v1/messages` 的 `message_start.usage.input_tokens` 用**请求体估算值**
（`protocol::anthropic::estimate_input_tokens`），`message_delta.usage` 用上游真实
`prompt_tokens` 覆盖；WB / Trae / Qoder 三条产品线的 Anthropic 出口全部接线。
另外 `handle_delta` 把 `capture_usage` 提到 `ensure_started` **之前** —— 上游若在首帧
就报用量，`message_start` 直接是真实值，估算不生效。

**理由**：Anthropic 协议要求 `message_start` **当场**给 `usage.input_tokens`，而上游
（OpenAI 兼容）只在**流末**报 `prompt_tokens` —— 时序上不可能同时满足。

- **不写 0 的代价**（即改造前的行为）：客户端（dsh / Claude Code）拿 `input_tokens`
  当上下文长度 ⇒ 占用率恒为 **0%**，用户看不出何时该 compact（#139 的全部体感）；
  `message_delta` 只给 `output_tokens` 时，连「本轮消耗」也只剩输出侧。
- **不引 tokenizer 的代价**：CJK 1 token/字、其余 3 字符/token 的估算误差约 ±15%。
  它只服务「要不要压缩」这个判断，**不是计费口径** —— 计费仍走上游 `usage`
  （`UsageTap` 那条路完全没动），所以估歪了不会算错钱。
- **不推迟 `message_start` 的理由**：那等于把整条流缓存到末帧，流式就没了；
  首帧带 usage 的情形已由上面的顺序调整免费覆盖。
- **为什么同时补 `cache_read_input_tokens`**：客户端把「缓存读取」单列一行，缺字段
  与「确实没命中」长得一模一样（都是 0）；四种上游写法
  （`prompt_tokens_details.cached_tokens` / `prompt_cache_hit_tokens` /
  `cache_read_input_tokens` / `cached_tokens`）收在 `cached_tokens_of` 一处。
