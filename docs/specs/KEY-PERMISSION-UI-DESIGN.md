|:--|:--|:--|:--|

## 1. 需求

issue #76「增加密钥访问权限管理功能」两条：

1. **根据密钥设置 token 可用量** —— 这把密钥最多能消耗多少。
2. **可限制密钥可访问的指定帐号列表** —— 这把密钥只能落到哪些账号上。

面向的用户是**把自己的网关分给别人用**的人：给自己写脚本、给同事发一把 key、给 CI 发一把 key。
今天这些 key 全是「万能」的——谁拿到都能用你的号、用你的额度，出了问题无法定位是谁用掉的。

## 2. 设计决策

| # | 决策 | 理由 |
|:--|:--|:--|
| D1 | **不新增页面**：权限挂在现有密钥行上，用右侧抽屉编辑 | 权限是**密钥的属性**，不是新资源。密钥分区现有形态是「工具条 + 裸表 + 说明段」（见 `src/components/gateway/api-key-table.tsx`），再加一页会让用户多学一次「去哪儿找」。 |
| D2 | **v3 重新设计（2026-10-22 真机截图返工）**：用量列压成**一行**（`已用 / 上限` + 3px 迷你条），权限列**只一枚账号 chip**，明细进**行内展开区** | v2 把「创建/最后使用」压到次行腾出两列，但用量列仍塞了四层文字（已用/上限、剩余、单位、周期）、权限两枚 chip 各占一行 ⇒ **单行 6 层文字全在换行**，行高翻倍，两列叠在一起整行密不透风（真机截图返工）。一览只承载「扫一眼就知道」的信息；单位/周期/剩余/账号名册是「想看才看」⇒ 点行展开，一次只展开一行。见 §3.0.1。 |
| D3 | 权限列用**两枚可点 chip**（额度 / 账号），不是一枚摘要 | 两枚 chip 各自独立可读（`额度 100万/自然月` `账号 3 个`），且**点哪枚就跳到抽屉的哪一段**。 |
| D4 | 配额 = **不限 / 限额（上限 × 重置周期）** | 见 U2。三档并列 radio 是「枚举」，两个控件是「维度」——后者能自然长出「自然月」而不用再加一档。 |
| D5 | 计量单位**二选一**（token / 请求数） | 见 U1。单位是**这把 key 的属性**，不是请求的属性 ⇒ 一次选定、始终一致。 |
| D6 | 数值单位**中文优先「万」**（`100万` 而不是 `1M`） | 中文语境里「100 万」比「1M」好读；≥1 亿才用 M。编辑框里同一个值不该在「100」和「1」之间跳。 |
| D7 | 账号范围两态：**全部账号 / 指定账号**（白名单） | 只有这两种，没有「排除某些」的第三态。白名单是**默认安全**的方向（漏配 = 不给权限，而不是给全量）。 |
| D8 | 白名单支持**按分组整组选取** | 见 U3。分组 chip 显示「已选/组内总数」，半选状态一眼可辨。 |
| D9 | 「指定账号」但**一个都没选** ⇒ **禁止保存** | 空白名单 = 这把 key 永远选不到号 = 静默 404/无号可用。用户以为配好了，实际全废。 |
| D10 | 把上限改到**低于已用量** ⇒ **允许保存**，但明确警告「保存后立即超限」 | 有时就是要立刻掐掉这把 key。拦着不让存反而让人绕路。但必须把后果说清楚。 |
| D11 | 超限的请求被拒（429），**只影响这把 key** | 错误体要写明是哪把 key、哪个单位、配额多少，让客户端能自己停；其它 key 不受影响。 |
| D12 | 创建对话框里也带这两项设置 | 否则用户得「先创建、再编辑、再保存」三步走。默认值仍是「不限 + 全部」，与今天一致。 |
| D13 | 三条产品线（WB / Trae / Qoder）与统一网关**共用同一构件与文案** | 仓库既有铁律：三个 Key 表共用 `KeysBar`、共用 `shared.gateway.keys.note`。本设计不引入第四份实现。 |
| D14 | **流式请求中途超额 ⇒ 优雅收尾** | token 是边走边计的：达到上限时发完 error 事件再断流，**不硬断连接**（硬断会让客户端看到「网络错误」而不是「配额用尽」，无法自愈）。 |
| D15 | 白名单内**暂无可用账号** ⇒ 明确报错，**不回退全池** | 回退 = 白名单形同虚设。错误文案要说清「白名单内的账号都不可用」，而不是笼统的「无可用账号」。 |
| D16 | **不新增导航项**：落在「网关 → 密钥」分区，编辑用**右侧抽屉** | 权限是**密钥的属性**，不是新资源。见 §3.0 的信息架构图。四个落点（WB / Trae / Qoder / 统一网关）共用同一抽屉构件。 |
| D17 | 抽屉里的**分组只引用不编辑**（分组本身仍在账号页维护） | 同一份分组两处编辑必然漂。抽屉只提供「整组选取」的入口与组名显示。 |

## 3. 信息架构

### 3.0 放在哪里（应用内位置）

```
左侧主栏  网关
  └ 二级子导航（随产品线不同）      独立网关：概览 · 密钥 · 模型 · 账号池 · 请求代理 · 请求日志
                                  统一网关：概览 · 命名空间 · 密钥 · 账号池
       └ 「密钥」分区 = 现有的钥匙表（工具条 + 裸表 + 说明段）
            └ 行内两枚可点 chip（额度 / 账号）→ 右侧抽屉 = 本次新增的全部交互
```

四个落点，**共用同一抽屉构件与同一套文案键**：

| 落点 | 页面组件 | 备注 |
|:--|:--|:--|
| WorkBuddy 网关 → 密钥 | `src/components/gateway/api-key-table.tsx` | 现有表 |
| Trae 网关 → 密钥 | `src/components/gateway/trae-api-key-table.tsx` | 现有表 |
| Qoder 网关 → 密钥 | `src/components/gateway/qoder-api-key-table.tsx` | 现有表 |
| 统一网关 → 密钥（`u-keys`） | `unified` 侧密钥表 | 该处 key 已有**命名空间授权** ⇒ 抽屉里是 **命名空间 → 账号范围 → 配额** 三段 |

**不新增导航项的理由**：新增一个「密钥权限」入口，用户得先想「这是网关的还是权限的」——
而权限本来就是密钥的一列。另两个「看起来该放这儿」的地方都更差：

- **设置页**：策略不是全局偏好，是**每把密钥**的属性 ⇒ 放设置页会变成"在设置里找某一把密钥"；
- **用量页**：用量是**结果**，策略是**原因** ⇒ 在用量页配配额属于因果倒置。

**唯一需要新位置的是 U4 的「按密钥看用量」**：它不进设置页，也不进密钥表，
而是**用量页加一个「按密钥」维度**（同一套账本 + 网关日志的 key 字段）——
它是"看"，不是"配"，与本功能解耦、可单独排期。

### 3.0.1 v3：一览与详情的分层（2026-10-22 返工后）

```
┌─ 一览行（每行只有两行文字）────────────────────────────────────────┐
│ 默认 Key           bs_live_9f3a••••7c21  国内版  620万/1000万▏  ●账号 全部  启用 │
│ 创建于 09-12 · 最后使用 2 分钟前                                      │
├─ 点行展开（一次只展开一行）───────────────────────────────────────────┤
│ 用量配额    620万/1000万 token · 自然月结算 · 剩余 380万    [编辑配额] │
│ 可访问账号  全部账号（8 个）—— 沿用网关当前的选号策略   [编辑范围]     │
└──────────────────────────────────────────────────────────────────────┘
```

三条规则：

1. **一览列不出现单位/周期/剩余** —— 它们是「想看才看」的信息。断言写成「列内**不得**出现」，
   防止被悄悄改回去（`verify-key-permission-main.cjs` 的「用量列压成一行」用例）。
2. **权限列一枚 chip**：额度上限已由用量列的 `/ 1000万` 体现，再写一枚「额度 1000万/自然月」
   是同一信息的第二次展示，纯占宽度。账号范围无法从别处推知 ⇒ 保留且可点（开抽屉账号段）。
3. **操作列 `data-stop`**：点「吊销」不冒泡成行的展开动作（否则点按钮旁边空白会顺手展开明细）。

### 3.2 列表的用量列

| 状态 | 判据 | 视觉 | 文案 |
|:--|:--|:--|:--|
| 正常 | `used/limit < 80%` | 主色进度条 | `62万 / 100万` + `剩余 38万` + 脚注「按 token 计 · 自然月结算」 |
| 接近上限 | `80% ≤ used/limit < 100%` | 警告色进度条 + 徽标 | 同上 + 徽标「接近上限」 |
| 已用尽 | `used ≥ limit` | 危险色进度条（满）+ 徽标 | `10万 / 10万` + 徽标「已用尽」 |
| 不限 | `mode = unlimited` | 无进度条 | `不限` |

脚注**必须写明单位与周期**（`按请求数计 · 每日 00:00 重置`）——「43万」这两个数在两种单位下含义完全不同。

### 3.3 抽屉

- **为什么是抽屉不是对话框**：要放分组 chip + 多选账号列表 + 三个数值控件，对话框会被撑到滚动；抽屉右侧展开、内容分区清楚，且与账号详情抽屉（`account-detail-drawer.tsx`）同构。
- **底部预览句**是必答题：保存前把后果说清 ——「保存后，『我的笔记本』的请求只会使用 3 个指定账号，配额 token 100万（自然月）。」
- **ESC / 遮罩可关**（与账号详情抽屉一致）。

### 3.4 账号选择列表

- 每行：勾选框 · 头像 · 名称 + 昵称 · 积分 · 所属组 · 状态（正常 / 冷却中 / 已禁用）。
- 搜索：按名称 / 昵称 / UID 三路匹配（与账号页搜索同口径）。
- 「全选」作用于**当前搜索结果**（不是全池）——用户搜完再全选，意图明确。
- 分组 chip：`主力号 2/2`（全选态带 ✓）、`备用号 1/2`（半选态）。点一下 = 整组切换。
- 已选 chips 区可单个移除；0 选中时区里写「还没有选择账号」。

### 4.2 网关侧错误文案

超额拒绝沿用既有错误信封风格（`GatewayError` / `openai_error`）：

```json
{"error": "quota_exceeded", "key": "my-laptop", "unit": "token",
 "used": 1000000, "limit": 1000000, "resetAt": null}
```

- `resetAt`：周期配额时给下一重置时刻（`null` = 不重置）。
- 白名单内无可用账号 ⇒ **不新增对外错误码**，仍是 `no_credential` / 401（`type_name` 是客户端分流依据，加类别等于改契约），
  靠 `cause` 区分：`ScopeEmpty`（名单口径，带 `pool_total` / `allowed` 与分类计数）+ 文案「这把 API Key 的允许名单只覆盖 N 个…名单外的账号不会被使用」，**不回退全池**。
  最初设想的独立码 `scope_no_account` **未采用**（2026-10-22 实现时定）。

## 5. 可访问性

- 抽屉：`role="dialog"` + `aria-modal` + 焦点移入 + ESC 关闭；标题与分区用 `h2/h3` 串成层级。
- 账号列表项：`role="checkbox"` + `aria-checked`，**空格/回车可切换**（原型已实现）。
- 分组 chip：按钮 + `aria-pressed`，文案带「已选/组内总数」——不靠颜色区分全选/半选。
- 进度条：`role="progressbar"` + `aria-valuenow/valuemin/valuemax` + `aria-label`（如「Token 配额，已用 62%」）。
- 颜色不是唯一信号：进度条之外始终有**数字 + 文字徽标**（接近上限 / 已用尽）。
- 所有可点 chip 同时是 `<button>`（原型用 `span.chip`，实现时换 `Button variant="ghost"`），键盘可达。

## 6. 数据契约（后端建议）

### 6.1 密钥记录扩展

`crates/buddy-switch-gateway/src/apikey.rs` 的 `ApiKeyRecord` 增补（**全部 `#[serde(default)]`**，老台账零迁移）：

```rust
#[serde(default)]
pub quota_mode: QuotaMode,        // Unlimited | Limited
#[serde(default)]
pub quota_limit: u64,             // 用量上限（Limited 有效）
#[serde(default)]
pub quota_unit: QuotaUnit,        // Token | Request
#[serde(default)]
pub quota_period: QuotaPeriod,    // None | Daily | Weekly | Monthly
#[serde(default)]
pub scope_mode: ScopeMode,        // All | Selected
#[serde(default)]
pub scope_accounts: Vec<String>,  // 允许访问的账号 uid（Selected 有效）
#[serde(default)]
pub scope_groups: Vec<String>,    // 允许访问的**分组** id（与 scope_accounts 并集）
```

`masked()` 的线上形态同步补：`quotaMode` / `quotaLimit` / `quotaUnit` / `quotaPeriod` / `scopeMode` / `scopeAccounts` / `scopeGroups` / `quotaUsed`。

> 统一网关侧（`unified/apikey.rs` 的 `UnifiedApiKeyRecord`）**同样要扩**：它已有
> `namespaces` + `biz_namespace` 的一维授权，再加配额与账号范围就是**三段**；
> UI 上按「命名空间 → 账号范围 → 配额」的顺序排（命名空间决定「能访问哪些平台」，
> 是最外层）。

### 6.2 用量计数

- 计数按**这把密钥**累计，落 `~/.buddy-switch/gateway_key_usage.json`：
  `{ keyId: { unit, total, periodKey, periodUsed } }`（`periodKey` = `daily:2026-10-22` / `weekly:2026-W43` / `monthly:2026-10` / `none`）。
- 记账点与用量页同源：`UsageTap`（流结束）——**不能**在请求前记（请求可能失败）；但**请求数**在请求进入时计（业务代理没有 usage 回包）。
- 周期重置按**本地时区**判定（`periodKey` 不等于当前周期 ⇒ 视为 0）。
- 配额判定点：请求**进入网关后、选号前**。超限 ⇒ 429，且**不消耗选号额度**（不占在途、不触发换号）。

### 6.3 选号与白名单

- 白名单是**硬约束**：在 `pick_account` 的候选过滤阶段剔除 `scope_accounts ∪ scope_groups` 之外的账号（与既有的 `excluded` 用户显式排除同层，但**来源不同**：一个是用户排除全局，一个是本 key 的允许集合）。
- 作用范围：**只对这把 key 的请求**生效；不改变账号池本身，不影响其它 key。
- 白名单里的账号若已冷却/禁用 ⇒ 视为不可用（不特殊照顾）；**全部不可用时明确报错，不回退全池**（D15）。

### 6.4 用量账本补「按密钥」维度（U4 的前置）

- `token_daily` 现有：client / gateway 两桶，gateway 桶的维度是 **密钥 / 模型 / 账号 / 端点**（密钥维度 v4 落地）。
- 要做「按 key 看用量」，需要网关请求日志里带 **key id**，并在账本增一个 `gateway_keys` 维度。
- 这一步**独立于本功能**：即便配额不做，用量页按 key 看排行也有价值；可先落地再接配额。

★ **2026-10-28 补：为什么必须进账本，不能只扫请求日志**（用户报障驱动的修正）

第一版实现（`2'` 标 ✅ 的那一版）为了省事，直接聚合 `get_gateway_logs` 的条目。
但那个日志是**环形缓冲**（保留最近 `log_keep` 条，缺省 200）—— 本机实测繁忙时
200 条只覆盖 **17 分钟**，而页面标的是「近 30 天」⇒ 出现
`44.2M Token / 200 次 / 100%` 这种**量级像真的、区间是假的**读数。

现在改为读账本维度（`token_daily::gateway_usage_dim` 的 `days[].keys`，
Trae/Qoder 走 `gateway_ledger::usage_dim`）：

- 桶键 `{keyScope}:{keyId}`；两个哨兵 `__legacy__`（升级前的条目，那时日志还没有
  `keyId` 字段）与 `__none__`（确实没带 Key）**分开统计** —— 与另外三个维度同轮
  同水位线产出 ⇒ 「按密钥合计 = 网关总量」仍是恒等式（单测守着）；
- 「没有该维度」（升级前的日期，空数组）与「用量为 0」在 UI 上**分别表述**：
  `keysPartial` + `keyCoverage` 披露覆盖天数与下界，绝不画成 0；
- 播种：升级当天 `gateway_keys` 为空而该日已有 token ⇒ 整窗补一次并标
  `keysPartial`（否则当天此前的请求全部漏记，看着像「这把 Key 只用了这么点」）。

## 9. 明确不做（本期）

- 配额**按模型**细分（不同模型不同单价/不同额度）。
- 账号范围的**排除模式**（黑名单）。
- **自定义周期**（如「每 7 天」「每 28 天」滚动窗口）—— 自然月 + 每周已够用。
- key 之间的**共享额度池**（多个 key 共用一个预算）。
- **按命名空间分别计量**（统一网关里一把 key 同时访问 LLM 与业务命名空间时，各算各的）—— 本期一把 key 只选一个单位。
- 审计日志（谁在什么时候用掉了多少）—— 依赖 §6.4 的 key 维度，另立 issue。

## 10. 2026-11-04 变更：明文可选保存 + 自定义密钥（推翻「一次性明文」）

「明文只在创建时返回一次、库里只存 sha256」不再满足。但「创建即无条件落盘」也不行 ——
是否把明文长期留在本机，必须由用户自己决定。这一节记录**被推翻的旧约束**与**当前口径**，
避免后人按旧文档改回去。

1. **创建时不得落盘明文**：`create_with_key` 里必须是 `plaintext: None`。
   门禁 `check-scope-registry.cjs` 的「明文可见性 + 创建后二选一」会盯这一条。
2. **`save_plaintext` 必须校验 `sha256(明文) == record.hash`**：前端把明文回传时
   传错（串了另一把 / 被截断）就拒绝写入，否则台账里会出现「眼睛显示的值根本不能用」。
   已有明文时幂等返回、不覆盖。
3. **`hash` 仍不下发**：列表 / 详情 / 日志都不得出现 `hash` 或其值（校验只认 hash）。
4. **没有明文的 Key 不渲染眼睛**：`plaintext` 为 `null` 时不给「点了没反应」的死按钮，
   也不从 `prefix` / `suffix` 反推、不补造明文。
5. **创建响应仍带 `key`**：它是「本次创建的那把」的权威值，自动化脚本依赖它
   （脚本拿不到面板，自行保存即可 —— 这正是改造前的行为）。
6. **`custom_key` 只 trim 首尾空格**：不补平台前缀、不改大小写。
   空串 / 纯空白 ⇒ 退回自动生成（后端 `resolve_key_plaintext` 兜底，不是前端判空）。
7. **掩码仍显示 `prefix••••••••suffix`**：眼睛是**额外**出口，不替代默认掩码。
8. **自定义密钥必须先查重**：`sha256(明文)` 与台账里任何一条记录相同 ⇒ 拒绝创建、**不落盘**，
   错误信息带上占用者的 Key 名称（`key_taken_message`，四条产品线共用一句话）。
   - 已吊销（`revoked_at.is_some()`）的记录**同样占用这个 hash**：那是同一把密钥的历史，
     正确动作是 `restore`，再建一条会让两条记录共用一个 `hash` —— 吊销一条、另一条仍能
     通过 `verify()`，吊销语义直接失效。
   - 校验挂在 `create_with_key` 入口（不是只写在某个 handler 里），两条通道与
     `create_response*` 帮助函数都绕不过去；门禁 A 项断言这一行必须存在。
   - 大小写 / 内容精确比较，不做归一化：`KEY-1` 与 `key-1` 是两把不同的密钥。
   - ⚠️ 查重是 **check-then-write**（读盘 → 比 hash → 推入 → `atomic_write`），
     没有跨进程文件锁，理论上两次并发创建能同时通过。当前靠前端「创建中禁用按钮」
     挡住重复点击；若将来加脚本批量创建，需要在 store 层补锁，而不是靠再查一次。
9. **HTTP 撞车一律 `400 + {ok:false, error}`**（四条产品线同一口径；IPC 无状态码，
   仍返回 `{ok:false, error}`）。Trae 的 HTTP handler 因此必须调
   `trae::apikey::create_result_with_key`（`Ok ⇒ json_ok` / `Err ⇒ json_err(BAD_REQUEST)`），
   **不得**写成 `json_ok(create_response_with_key(...))` —— 那会把撞车变成 `200`，
   与 WB / Qoder / Unified 三条线的 `json_err(400)` 分叉（webui fallback 尤其能看出差别）。
   成功体仍由 gateway 的 `created_payload` 唯一拼装，通道层不拼形状（`trae-parity-design.md` §5.4）。

### 10.3 `data-act` 命名约定（e2e 选择器）

面板里的复制按钮与列内眼睛展开后的复制按钮**长得一模一样**（都是 `<Copy />`），
改造前共用 `data-act="gw-key-copy"` ⇒ 选择器命中两个，取到哪个看渲染顺序。按作用域分名：

| `data-act` | 位置 |
|:--|:--|
| `gw-key-secret` | 列内「掩码 + 眼睛」容器 |
| `gw-key-reveal` | 列内眼睛（显 / 隐切换） |
| `gw-key-reveal-copy` | 眼睛展开后的复制 |
| `gw-key-panel-copy` | 创建后二选一面板里的复制 |
| `gw-key-panel-save` | 面板「保存到本软件」 |
| `gw-key-panel-dismiss` | 面板「自行保存」（= X / ESC / 遮罩） |

跨文件的同名是**设计如此**（四张表各带一份面板，Radix 对话框关闭时不渲染内容）；
同一个文件内必须唯一 —— 门禁会逐文件统计 `data-act` 出现次数。

⚠️ **行内元素天然重复**：`gw-key-secret` / `gw-key-reveal` / `gw-key-reveal-copy` 挂在每一行里，
一页有 N 把 Key 就有 N 份。这不违反上面的规则（门禁统计的是源码出现次数），但 e2e 不能
直接 `page.locator('[data-act="gw-key-reveal"]')` —— 必须**先定位行**再在行内取
（`row.locator('[data-act="gw-key-reveal"]')`），否则命中 N 个、`click()` 直接报 strict mode 冲突。
面板三件套（`gw-key-panel-*`）在任一时刻最多一份（对话框关着就不渲染）。

### 10.4 安全边界

- **保存过的 Key**：明文在 `~/.buddy-switch/**/api_gateway_keys.json`。POSIX 侧由
  `atomic_write` 强制 `0600`；Windows 靠 `%USERPROFILE%` 的 ACL。备份 / 同步盘 /
  同机其他进程仍可能读到 —— 这是用户在面板里的显式选择。
- **没保存的 Key**：磁盘上只有 `sha256`，与改造前同等级。
- 无论哪种，**校验链路都只认 hash**（`verify()` 用常量时间比较），明文不参与鉴权。

⚠️ **管理面暴露 = 明文暴露（本次新增的风险面）**

`GET /api/{gateway,trae/gateway,qoder/gateway,unified-gateway}/keys` 现在会带上
`plaintext`。管理面的 `api_guard` 只做 Host / Origin 校验（防 DNS rebinding），**不做身份认证**。
因此：

- 只绑 `127.0.0.1`（默认）：本机任何进程 `curl` 都能读到全部**已保存**的明文。
  改造前它只能读到掩码 —— 这是本需求带来的实际降级，已在面板里由用户显式选择承担。
- 一旦按 `LINUX-WEBUI-FALLBACK.md` 改成 `0.0.0.0` + `BUDDY_SWITCH_ALLOWED_HOSTS`，
  **局域网内任何设备都能直接拉走明文**。开启前必须确认网络可信；不信任的网络里应保持
  回环绑定，或让用户对所有 Key 选「自行保存」（这样列表里没有明文可漏）。

### 10.5 数据兼容

- `plaintext` 走 `#[serde(default)]` ⇒ 旧台账（无该字段）读出 `None`，**不迁移、不报错**。
- 磁盘形状未变（仍是同一个 JSON 数组），新增字段排在 `hash` 之后。
