但用户实际请求仍报 11-128。有一条能收敛的差异：

- 用户拿到的 `requestId` 是 **`8d6c73fb9de944d1956c79bb26b16f8c`（32 位无横线 hex）**

## 现象二：Qoder CN 报「没有可用账号」，但账号全部可用

账号页 4 个 Qoder CN 账号全部显示「凭据可用 / 设备码登录」，`qoder/accounts.cn.json` 里 `accessToken`（`dt-` 前缀）与 `refreshToken`（`drt-` 前缀）都在，`expiresAt` 均未过期。

`GET :57895/health` → `{"ok":true,"risk":{"exhausted":0,"queued":4,"rateLimited":0,"rejected":0}}` —— **queued = 4，四个号全在排队态**。

历史 `qoder/logs/gateway_requests.jsonl`（200 条）：116×200、51×503、33×429。503 的 error 文案即「Qoder CN 没有可用账号」；429 的上游原文是 `{"code":"403","message":"{...\"subCode\":\"RESOURCE_LIMIT\"}"}`（队列限流）。

对应源码 `crates/buddy-switch-gateway/src/qoder/routes.rs:1046-1049`：`failures.is_empty()` 时才给「没有可用账号」文案。⇒ 意思是**一个号都没被选中过**，不是「全部失败」。那被什么挡在选号之前？请作者看下 `pool.pick()` 与 `account_blocked()` 这段。

## 网关侧三个缺口（顺带反馈）

### 1. `log_bodies` 是死开关，用户打不开也抓不到上游原文

`gateway_config.json` 的 `log_bodies` 默认 `false`。用户按 FAQ 提示想打开它抓 400 的上游原文，但：

- `crates/buddy-switch-gateway/src/logging.rs:278 pub fn log_bodies()` **全仓无消费者**（grep 只有定义与 `set_log_bodies`）
- `docs/specs/CACHE-HIT-RATE-PLAN.md:80` 也明文写着「`log_bodies` 是死开关：全仓无消费者 ⇒ 从未落过正文」

⇒ 打开它也不会多出正文。建议要么接上消费者，要么从 UI/FAQ 里去掉这个开关。

### 2. 400 的上游错误体没有任何落盘位置

`crates/buddy-switch-gateway/src/logging.rs:322 append_usage()` 只挑 13 个字段写 `gateway_usage/<day>.jsonl`，**明确不含 `error`**（注释：error 可能带上游原文，统计不需要）。

而 `gateway_logs.json` 的 `error` 字段语义（#129）= 流中途失败时的上游摘要，`None` = 正常结束。⇒ 400 记录的 `error: null` **不代表网关没拿到上游体，而是没地方落**。

上游错误体在 core 层其实有留：`crates/buddy-switch-core/src/modules/upstream.rs:26 const ERROR_BODY_LIMIT: usize = 4096`，但到 gateway 层被 `error.rs:648 truncate_upstream_message()` 截到 400 字符，只出现在「客户端响应体」里。

建议：给非 2xx 的上游体加一个可选落盘（哪怕只保留最近 N 条），或把 `log_bodies` 真正接上。

### 3. `risk_controls_by_region` 的默认值可能过于激进，且本地拦截会写进账号冷却

`gateway_config.json` 里的默认值（`crates/buddy-switch-core/src/modules/risk_control.rs:34-40` 的 `RiskControlSettings::default()`）：

```json
"cn":     { "requests_per_minute": 30, "max_in_flight_per_account": 1, "max_in_flight_global": 1, "min_account_gap_ms": 5000, "max_transient_attempts": 2, "fallback_cooldown_secs": 60 },
"global": { "requests_per_minute": 30, "max_in_flight_per_account": 1, "max_in_flight_global": 1, "min_account_gap_ms": 5000, "max_transient_attempts": 1, "fallback_cooldown_secs": 60 }
```

效果：cn 全域**同时只允许 1 个在途请求**，同一账号两次请求间隔 ≥ **5 秒**。客户端并发/重试时大量请求被本地拦成 429：

- `请求被风控准入拦截：global concurrency limit reached`
- `请求被风控准入拦截：per-account concurrency limit reached`
- `请求被风控准入拦截：minimum account request gap not elapsed`

这正是账号卡片上那行红字的来源。

更麻烦的是 `crates/buddy-switch-core/src/modules/risk_control.rs:331`：这类**本地自造**的拦截被记成 `AccountRiskState::Cooling`（`RiskOutcome::RateLimited`），**持久化到 risk state 文件**，`fallback_cooldown_secs` 默认 60。⇒ 本地并发限制反过来让账号进入 60 秒冷却，形成自我加剧。

建议：本地准入拦截不要写成账号冷却（它不是上游给的限流），或至少区分 `local_rate` / `upstream_rate` 两种来源。
