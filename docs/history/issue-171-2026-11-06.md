# Issue #171：账号可用却误标需重新登录

> 状态：只读历史（不再更新） · 原始记录日期 2026-11-06

> 用户报障（2026-11-06，附截图）：账号能正常切换、查积分、走网关，卡片上却同时挂着
> 「当前登录」与红色「需重新登录」。实测该账号凭据**完全健康**，徽章是误标 + 滞留的产物。
> 主干 `1707fae1` 未修复。涉及 `crates/buddy-switch-core/src/modules/refresh.rs`、
> `src/lib/use-workbuddy-status-refresh.ts`。

## 1. 现象

账号卡片（WorkBuddy 国内版）：

- 右上角：「当前登录」（绿色）
- 状态位：**「需重新登录」**（红色 destructive 徽章）
- 积分 2,905.73/4,510，用量时间「刚刚」——一切读写正常
- 用户操作验证：切换该账号成功、官方接口全部可用

「当前登录」与「需重新登录」同屏矛盾，且按用户的话说「我明明登录是有效的」。

## 2. 根因（两条独立成立，叠加成完整症状）

### 2.1 后端：刷新失败不分类，网络抖动也会落 `needs_relogin`

`refresh.rs` 的 `refresh_account_token_for`（主干 `1707fae1` 约 127–140 行）对刷新失败的
处理是**一把抓**：

```rust
let code = resp.get("code").and_then(|v| v.as_i64()).unwrap_or(-1);
if code != 0 && code != 200 {
    account["needs_relogin"] = json!(true);      // ← 所有失败都落标记
    account["needs_relogin_reason"] = json!(...);
    ...
}
```

而 `http_request`（`config.rs:1100` 注释即契约）的失败语义是三类的：

| 来源 | `code` | 能否证明凭据坏了 |
|:--|:--|:--|
| 网络层错误（超时/连接失败/代理不可用） | `-1` | **不能** |
| HTTP 错误且 body 不可解析（CDN/代理的 5xx 错误页） | `<http status>`（502/503/504…） | **不能** |
| 服务端业务拒绝（如 12153 invalid_grant、401/403） | 业务码 | 能 |

前两类发生时 access token 往往仍然有效（账号照常切换、查询、走网关），却被落了
`needs_relogin=true`。又因为该标记**只在刷新成功时清除**（`refresh.rs` 成功路径
`map.remove("needs_relogin")`），一旦误标就要挂到下一次保活成功——默认配置下
保活一天一轮，徽章一挂就是最长一整天。

标注记也不会无限重试：惰性刷新由 `expiresAt` 门槛（`ensure_fresh_token_for` 的
`lazy_refresh_hours`）节流，保活一天一轮——「避免无限重试」这个标记的设计初衷
并不依赖「把暂时性失败也判死」。

### 2.2 前端：60 秒轮询只刷 status，标记清除后徽章不恢复

`use-workbuddy-status-refresh.ts` 的轮询 tick 只调 `refreshAllStatus`
（`/api/status`），而 `needsRelogin` 只存在于**账号列表**响应（`account.rs:283`
的 `account_meta` 映射，来自账号库 `accounts.json`）。账号列表只有页面加载、
导入本机、切换账号等动作才会重拉。

于是时间线是：

1. 某次刷新遇到网络抖动 → `needs_relogin=true` 落进账号库 → 页面显示「需重新登录」；
2. 当天保活成功 → 标记从账号库**清除**；
3. 打开着的页面**永远不知道**第 2 步发生了 → 徽章滞留，直到重开页面/重开窗口。

## 3. 实测证据（脱敏）

2026-11-06 上午核验报障用户本机（桌面安装版，数据目录 `%USERPROFILE%\.buddy-switch`）：

| 核验项 | 结果 |
|:--|:--|
| 报障账号（uid `72debddc…`，手机号已打码）在 `accounts.json` 中 | `needs_relogin` 字段**不存在**（健康态） |
| `access_token` / `refresh_token` | 均在（明文，非信封） |
| `refreshedAt` | 2026-11-06 01:00（当天保活成功） |
| `expiresAt` | 2026-12-06（一个月后） |
| 同日页面 | 仍显示「需重新登录」→ **UI 滞留实锤** |

复现路径（两步都必要）：

1. 让某账号的刷新请求失败一次（断网/代理抖动均可，`code=-1`）→ 账号库落标记、卡片变红；
2. 恢复网络，等下一次保活成功（或手动等标记被任何一次成功刷新清除）→ 磁盘已健康，
   但**不重开页面**的话徽章永远不消失。

附注（观测性缺口）：保活单账号结果是**不会**落运行日志的（`logs/runtime-*.log`
里搜不到 keepalive 记录，只在排程面板返回值里存在），所以「当初为什么被标」在
事后无法复盘——本例中原始失败原因已不可考，但与 §2.1 的机制完全吻合。

## 4. 影响

- **误导用户**：健康账号被引导去「重新登录」，实际重登解决不了任何问题
  （凭据没坏）——报障人原话「这是什么问题，是真的 token 过期了吗」。
- **污染排障方向**：`needs_relogin` 是账号库的持久状态，会进备份统计
  （`backup.rs` 的 `count_needs_relogin`），让「需重新登录 N 个账号」的统计虚高。
- 网关 pool 的三振/拒绝体系是另一套（`pool/entry.rs`），不受此标记影响——
  但网关侧同样会因为代理抖动产生瞬时失败，若有人参照本标记做排查会被带偏。

## 5. 建议修法

### 5.1 后端：刷新失败按「暂时性 / 凭据被拒」分流

```
is_transient_refresh_failure(code) = code < 0 || (500..=599).contains(&code)
```

- 命中 → **不落** `needs_relogin`（不改动账号库的标记语义）；失败详情挂在
  **返回值**（如 `refresh_transient_error`，不落盘），保活结果状态单列
  `transient`（不是 `ok` 也不是 `failed`），下一轮保活自然重试。
- 未命中（业务拒绝码）→ 照旧落 `needs_relogin`。
- 成功路径顺手清掉返回值上的临时字段，防止调用方复用返回值落盘时残留。
- `run_keepalive_cycle_for` 的结果映射同步：`failed` / `transient` / `ok` 三态。

### 5.2 前端：轮询补上账号列表

- 轮询 tick（`use-workbuddy-status-refresh.ts`）在 `refreshAllStatus` 之外同时
  `reconcileAccounts` 两个 region（store 层加一个合体入口即可）——走的是
  `reconcileAccounts`，不触碰 `loading`，不会闪骨架屏。
- 手动「刷新 Token」的 toast 对暂时性失败给 **warning**（凭据没坏但 token 没换成新），
  既不冒充成功、也不复用「需重新登录」的 error 文案。

## 7. 验收标准

- [ ] 网络层失败（`code=-1`）后，`accounts.json` **不得**出现 `needs_relogin=true`（用例断言）
- [ ] HTTP 5xx 错误页（body 不可解析 → `code=<status>`）同上
- [ ] 业务拒绝码（12153 invalid_grant、401/403）**仍**落 `needs_relogin`（阳性对照用例）
- [ ] 保活结果对暂时性失败报 `transient`（携带可读原因），不得混入 `failed`/`ok`
- [ ] 后台清除标记后，**不重开页面**的情况下徽章在下一个轮询周期（≤60s）内消失
- [ ] 手动「刷新 Token」遇暂时性失败：显示警告（含原因），不显示「需重新登录」，不谎报成功
