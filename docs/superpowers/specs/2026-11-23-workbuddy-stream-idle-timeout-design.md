# WorkBuddy 流式转发 idle 超时设计

> 状态：现行（2026-11-23）

## 意图

修复统一网关转发 WorkBuddy CN 流式请求时，上游首帧之后长时间不再发送字节，导致客户端等待接近 reqwest 默认 300 秒读超时的问题（issue #208）。

## 目标与边界

- 在每个上游字节到达时重置 idle 计时；默认 60 秒。
- 提供 `BUDDY_SWITCH_STREAM_IDLE_TIMEOUT_SECS` 环境变量覆盖；设为 `0` 时禁用。
- 超时后及时结束流，并按现有协议错误语义向客户端发送错误帧和终止帧。
- 在请求日志中记录 idle 时长和超时前已向下游转发的字节数，便于后续调整阈值。
- 不在已发送响应头、已开始输出的 SSE 流中切换账号重放；不改变非流式请求的超时策略。

## 方案

在流式字节转发层增加可配置的 idle 超时包装，按上游字节而非解析出的 token 或内容 delta 计时。超时事件接入现有流失败信号与错误帧出口；SSE 响应头已经提交后无法再改 HTTP 状态码，因此用错误帧明确报告失败并结束流。

考虑过只调大或调小 reqwest 的全局 read timeout，但它不能表达“相邻上游字节之间的空闲时间”，也会同时改变非流式请求行为，所以不采用。流已开始后由网关换号重放会把两条上游响应拼进同一个客户端响应，可能重复角色帧或混合响应 ID，因此本次不做流内 failover。

## 约束与待实现细节

- 60 秒、环境变量名和 `0` 禁用语义来自 issue #208 的报告者与维护者讨论。
- 保留现有 usage 采集、错误治理和 `[DONE]` 终止规则；idle 超时必须按流失败记录，不得静默结束成“成功”。
- 实现时需确认 auto-failover 关闭态仍会向客户端显式报告 idle 失败；该开关只控制既有治理/错误帧策略时，不能让 idle 超时退化成静默截断。
- 字节计数只统计已交给下游的上游字节，不包含生成的错误帧。
